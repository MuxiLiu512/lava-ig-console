# 自我審查點（正本）

發布前必檢清單。**機械可驗的走本機檢查**（`sync_console.py copy-check`，零成本、每次渲染自動跑），
**需要判斷的走成篇總檢**（WF15 vision）。兩者結果都寫進 `posts.json` 並顯示於操控室。

規則來源一律標註提出者與日期；規則只增不刪，失效者標 `retired` 並註明原因。

## A. 封面（最高權重——決定滑不滑得下去）

### A1. 標題必須帶主題，不得只有公版開場 〔Jesse 2026-08-10〕
**症狀**：川口春奈篇封面主標只有「欸，你有沒有發現」，讀者不知道要發現什麼；真正的主題（日系清冷感／塩顏）縮在下方小字。
**規則**：封面主標必須包含該篇主題的具體名詞（人名／專有名詞／現象名）。對話式開場只能當**前綴**，不能是整句標題。
- ✗ 「欸，你有沒有發現」
- ✓ 「欸，你有沒有發現——台灣正在瘋日系『塩顏』」
**機械檢查**：主標與 topic 若無任何 2 字以上共同詞，且命中公版開場樣式 → 標記 `hollow_hook`。

### A2. 對話式開場不得連續濫用 〔Jesse 2026-08-10，衍生〕
**症狀**：WF01 prompt 鼓勵「欸…你有沒有發現」，導致多篇同開場，帳號辨識度變成模板感。
**規則**：同一種開場句型近 5 篇最多出現 1 次。
**機械檢查**：比對近 5 篇封面主標前 6 字，重複 → 標記 `hook_repeat`。

### A3. 副標每行必須語意完整，不得詞中斷行 〔Jesse 2026-08-10〕
**症狀**：「最近讓台灣人最／心動的臉，都不太／需要你喜歡她」——「最心動」「不太需要」被拆兩行。
**規則**：斷行優先在標點；行尾不得停在修飾詞／連接詞（最、不、很、更、也、都、又、再、還、就、才、的、地、得…）。
**已修**：引擎 `wrap_semantic()`（2026-08-10）語意優先斷行；本檢查作為回歸驗證。

### A4. 副標不得句中截斷 〔Jesse 2026-08-03〕
封面渲染區有限，寧可整句退行也不留半句。**已修**：`sub_lines[:6]` + 句尾標點回退。

## B. 成篇（單張看不出來，合起來才露餡）

### B1. 主體重複 〔Aziz 事件 2026-08-06〕
同一本書／同一個人／同一件物品跨張出現（即使背景、載體不同）＝ block。
**判準校準中**：「同類型但不同主體」（例如都是人像、都是劇照）應為 warn 而非 block——
2026-08-10 觀察到同一篇兩次判定不一致，需收斂 WF15 prompt（待 n8n 連線恢復）。

### B2. 浮水印／圖庫殘留 〔Aziz 事件〕
alamy／getty／shutterstock／Magnific／Mindframe 等字樣或平鋪 logo ＝ block。
**上游防線**：`forage_shots.py` STOCK_BLOCK 網域黑名單（發現一個補一個）。

### B3. 文字不可讀 〔Gottman 事件 2026-08-10〕
底圖過花或明暗對比不足導致疊字難讀 ＝ block。網頁截圖當滿版底圖是高風險來源。

### B4. 出處標示異常 〔Aziz 事件〕
圖上「圖片來源」不得是內部檔名／亂碼（`a-mooddfeba`）。**已修**：內部標籤樣式一律留白。

## C. 字型與渲染

### C1. 缺字偵測 〔川口春奈事件 2026-08-10〕
**症狀**：品牌字型無日文新字體漢字（塩顔坂学）與中線刪節號（⋯），畫出來是空白，靜默吞字。
**已修**：引擎缺字備援層（`_segments`／`_text_fb`），偵測到主字型缺 glyph 才改用系統日文字型。
**機械檢查**：渲染前掃描文案，若有字在主字型與備援字型皆缺 → 標記 `missing_glyph`。

## D. 流程完整性（改了卻沒生效的坑）

### D1. 排程後的文案修改必須觸發重出 〔Jesse 2026-08-11〕
**症狀**：川口春奈已排程後改文案，`render_approved` 因「已排程且成品齊 → 不動」直接跳過，
WF10 到點把**舊版**發上 IG（media 18068504714733425），封面仍是未修正的空洞 hook 與詞中斷行。
**規則**：scheduled 狀態下，若 copy_edits／reviews 的 ts 比 `rendered_at` 新 → 必須重出成品。
**已修**：`render_approved` 排程 skip 加例外判斷（2026-08-11）。
**不可逆提醒**：IG 貼文的**圖片發出後無法替換**（caption 可在 IG 手動編輯）。排程前務必確認成品即最終版。

### D2. 未儲存的文案修改必須顯眼 〔Jesse 2026-08-11〕
**症狀**：操控室改了文字但未按「儲存文案修改」，系統無任何紀錄（git log 無 copy-edit commit），
使用者以為已生效。
**已修**：按鈕即時顯示「（N 處未儲存）」＋橘色脈動、離開頁面攔截、排程中貼文顯示不可逆警告。

### D3. 引擎修復後，已排程稿必須重出 〔2026-08-11 自省〕
引擎層修復（缺字備援、語意斷行）只對「之後渲染的成品」生效。
修引擎後必須主動重出所有 approved／scheduled 稿，否則排程中的舊成品帶著已修好的 bug 發出去。
本次川口春奈即因此發出仍有斷行問題的封面。

### A5. 主標斷行同樣不得拆詞 〔2026-08-11〕
封面主標走的是多色片段路徑（`wrap_segments`，需支援【】重點色），與副標不同函式，
第一次修語意斷行時漏掉 → v2 首渲出現「都變／最近讓人心動」把「最近」拆兩行。
**已修**：`wrap_segments` 斷行前回退，行尾若停在修飾詞則整個詞推到下一行。

### A6. hollow_hook 判準：剝開場看剩餘內容，不比字面共詞 〔2026-08-11〕
初版用「主標與 topic 有 2 字共詞」判定，主標改用同義說法時誤報
（「最近讓人心動的臉，都變『冷』了」與 topic「日系清冷感…」無共詞卻被判空洞）。
**已修**：剝掉公版開場後剩餘實質內容 <6 字才算 hollow。四個邊界案例回歸通過。

### D4. 重做已發佈貼文必須換 post id 〔2026-08-11〕
WF10 以 post id 記錄「已發佈」於 static data。沿用同 id 重做 → 新版排程後被去重靜默擋住不發。
**規則**：重做一律用新 id（`YYYYMMDD-主題v2`），舊版 `archive-post` 留紀錄；
同時把 ClickUp 卡狀態從「發佈完成」退回「在製中」，否則 `reconcile-published` 會把新版誤翻成已發佈。

### A7. 行尾標點一律刪除 〔Jesse 早期規則，2026-08-11 才完整落實〕
**症狀**：規則早就提過，但引擎的 `strip_trailing_punct` 只處理「文案原本的換行」，
排版當下才決定的斷行沒被處理 → 逗號掛在行尾（Aziz 篇「…威奇托等地，」）。
**已修**：`strip_line_ends()` 對排版後的實際每一行清尾標點，套用於主標／副標／內文／來源四處。
刪除 `，、；：。．,;:` 等分隔標點；保留 `」』）〗】` 成對閉合符號與 `？！` 語氣符號。

### A8. 排版規則要有機器驗證，不能靠看圖 〔Jesse 2026-08-11 質疑〕
「說修好了但沒效」發生過兩次，肉眼抽看幾張不構成證明。
**已建**：`scripts/check_typography.py` 載入引擎本身的斷行函式重算每一行，逐行驗三項規則
（行尾標點／詞中斷行／缺字），並套用操控室的文案編輯後才檢查——驗的是「實際會印出來的版本」。
已掛進哨兵每輪自動跑。
**判準分離**：引擎的 `NO_TRAIL` 刻意放寬（斷行多回退一格無害）；檢查用 `CHECK_NO_TRAIL` 嚴格子集，
排除「地／是／對／想」等歧義字，否則「威奇托等地」會被誤報。首版即因此誤報 26 處。

### D5. 每一步都要有 timeout，否則 launchd 會讓整條線靜默停擺 〔2026-08-17 事故〕
**症狀**：`ingest-new` 卡在 Google Drive 讀檔，**21.5 小時**沒有任何一輪跑完。
launchd **不會併發啟動同一個 job**，所以後續每一輪都沒有開始；而卡死的那一輪什麼都沒印，
log 完全沒有新行——**「沒有訊息」與「一切正常」長得一模一樣**。
**已修**：`auto_render.sh` 每個 python 步驟包 `timeout`（一輪最壞 68 分鐘必定結束）；
另加「未完成輪次」標記，下一輪偵測到「開始了卻沒結束」就告警到 ClickUp 並指出卡在哪一步。
**判準選擇**：用「開始了沒結束」而不是「兩輪間隔過久」——後者會把筆電睡眠誤報成卡死。
**通則**：靜默停擺已發生三次（8/03 git 兩天、8/16 讀檔 21.5 小時）。
任何會被外部資源阻塞的步驟（網路、雲端掛載、子程序），沒有 timeout 就等於沒有哨兵。

### D6. 取樣窗口不得用「最新 N 份」代替「還缺什麼」 〔2026-08-17〕
**症狀**：`forage-pending` 取「最新 8 份草稿」，但 8/08 那批就有 10 份 →
8/03 那批 7 篇**永遠排不進窗口**，產品機制圖解缺 s2/s7 卡了兩週沒人發現。
**已修**：窗口 8→40，並改成正面表列（只處理有對應**待審**貼文的草稿）。
已補齊者在 missing 判斷即 `continue`，成本只有幾次 glob；
純放大窗口會連 16 份沒有對應貼文的舊稿一起抓，所以必須配正面表列。
**同時修**：排除 Drive 同步產生的同名副本 `… (1).json`，否則同一篇被抓兩次。
**通則**：佇列類的挑選條件要寫「還缺什麼」，不要寫「最近的幾個」——後者會製造永久死區。

### D7. 讀不到稿 ＝ 這篇完全沒被檢查，必須當違規 〔2026-08-17〕
**症狀**：產品機制圖解的 Drive 草稿被硬截斷（WF01 舊 maxTokens 8000 的遺留），
`forage-pending` 與 `check_typography` 都只印一行 `⏭ 讀稿失敗` 就跳過，
於是那篇兩週來從沒被驗過排版，而報表照樣顯示「違規 0 處」。
**已修**：`check_typography` 把讀稿失敗列成 `🔴 稿檔損毀` 並計入退出碼，哨兵 grep 得到。
**附帶發現**：同一天 WF01 跑了兩次，14:06 的完整版被截斷、14:29 的重跑版較差卻成為操控室內容。
**通則**：驗證工具遇到「無法驗證」時，預設必須是**失敗**而不是**略過**。
略過會讓覆蓋率缺口偽裝成合格率，這與 A8／A9 是同一類錯誤。

## E. 使用者信心（改了不知道有沒有生效、不知道等多久）

### E1. 文字框與圖片必須看得出誰是真的 〔Jesse 2026-08-12〕
**症狀**：文字框顯示原始文案（含破折號、原始換行、【】標記），圖上是清理＋重新斷行後的結果，
兩者不同 → 「我不知道哪邊才是正確的」。
**已修**：`sync_console.py rendered-lines` 用引擎本身的斷行函式算出「圖上實際呈現」，
寫入 `posts.json.rendered_lines`，操控室在每個文字框下方以唯讀區塊顯示。
**注意**：存在 post 層而非 `slides[]`——渲染流程中途會 refeed 重建 slides，寫在裡面會被沖掉。

### E2. 改圖／改文案後必須知道「何時真的完稿」 〔Jesse 2026-08-12〕
**症狀**：哨兵 10 分鐘一輪，改完立刻看當然沒更新，但使用者無從得知系統收到了沒、要等多久。
**已修**：①操控室卡片顯示「🔄 正在依你的修改重出成品…完成後自動恢復排程」
②重出完成即在 ClickUp 卡留言並推播（附張數、排程時間、總檢結果、操控室連結）。

### E3. 核准後不得清掉已設好的排程 〔Jesse 2026-08-12〕
**症狀**：已排程貼文改圖再核准 → `app.js` 無條件把 status 設回 approved，
publish_at 雖仍在但 WF10 只發 scheduled，看起來像「排程消失、要重設時間」。
**設計**：降回 approved 是**必要的**——成品還沒更新前若維持 scheduled，到點會發到舊圖。
**已修**：`render_approved` 重出完成後，若 `status==approved 且有 publish_at` → 自動恢復 scheduled。
降級有了回程，使用者不需要重設時間。

### E4. --only 與 --force 的順序 〔2026-08-12〕
`--only` 原本排在排程 skip 判斷之後 → 其他篇的訊息會混進單篇執行的輸出；
`--force` 對已排程貼文無效 → 想強制重出時靜默跳過。兩者已修正。

### A9. 檢查工具必須用引擎的字級常數，不可自行猜 〔2026-08-13 自省〕
**症狀**：`check_typography.py` 封面主標寫死 `W*0.043` / `max_w=W*0.86`，
引擎 `render_cover` 實際是 `W*0.075` 起跳、逐級 ×0.92 縮到 `W*0.05`、寬度 `W*0.89`。
字級只有引擎的 57%，算出的斷點與印出來的完全是兩回事。
**所以 2026-08-12 那次「9 篇全過、違規 0 處」是假的**，它驗的不是實際會印出來的版本。
這正是 A8 宣稱要避免的事，卻由 A8 自己犯下。
**已修**：字級決定邏輯抽成引擎的 `cover_title_lines()` 公用函式（含動態縮字），
渲染與檢查共用；版面常數 `COVER_TITLE_FS` 等集中宣告。修正後重驗 15 篇仍 0 違規。
**通則**：任何「驗證產物」的工具，只要自己重算了產物的生成參數，就等於在驗另一個東西。
一律呼叫生成端的函式，不要複製它的數字。

## F. 設計版型（產品介紹）

### F1. 版面位置不得硬寫分數值，要用間距階梯＋內容帶 〔Jesse 2026-08-17〕
**症狀**：`render_product` 第一版每個版型各自寫死 y（`cy=0.52`、`by0=0.335`…），
結果剩餘空間全部堆在版面下半部變成大片空洞，各張之間的留白也對不齊。
**已修**：間距只能取自階梯 `S_XS/SM/MD/LG/XL`（8px 網格 ×3 = 24 為基準）；
版面結構固定為 logo → GAP_HEADER → 導言 → GAP_LEAD →〔內容帶〕→ GAP_STAGE → 大標 → GAP_TITLE → footer，
視覺元件**置中於內容帶**，空白由系統平均分配。
**通則**：留白是被分配的，不是被剩下的。任何新版型都必須吃 `band` 參數，不得自訂 y。

### F2. 產品介紹的素材＝自家品牌照片，產品感由設計元件承擔 〔Jesse 2026-08-17〕
**症狀**：產品介紹被當成知識型貼文，forager 去網路抓別人的照片來講自己的功能。
**修正過程（我第一次也判斷錯）**：先改成塞真實 App 截圖，但 375px 的 @1x 匯出
放進手機卡後介面內容小到看不清。回頭比對 Jesse 的參考稿才發現——
**那五張裡根本沒有 App 截圖**，卡片裡是真人照片，「產品感」是由設計元件承擔的
（紅框、星標徽章、模擬通知卡、卡片堆疊圖解）。
**規則**：`template_id == tpl-product-intro-carousel` 的稿不走 forager。
媒體版位取自 Drive `02_Marketing/02_行銷素材庫/`（宣傳照 4000×4000、
現場攝影 8448×6336，都是縮小不是放大）；UI 感一律用引擎畫的元件。
App 截圖只在「這一張的重點就是那個介面」時才用，且必須裁到有意義的區域放大，
不可整螢幕縮小。
**通則**：使用者說「要有截圖的樣子」時，先確認他要的是**截圖本身**還是**截圖的視覺語彙**。
拿他給的參考稿逐張比對，比照字面理解可靠。

### F3. 產品大標保留作者手打的行尾標點 〔2026-08-17〕
A7「行尾標點一律刪除」針對的是**排版當下造成的斷行**。產品大標是手寫短句，
作者打的 `\n` 後那個句號是語氣的一部分（參考稿「不只喜歡你。／這次約會，我請。」）。
**規則**：同一段被寬度拆開才清行尾，段落自己的結尾原封不動。知識型貼文不受影響。
