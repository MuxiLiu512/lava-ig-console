# 0. 三個必須先講的前提修正

這三件事會改變後面所有數字，先講。

## 0.1 產能是 12 篇/月，不是 30 篇/月

S2 的月成本算 30 篇（$22 到 $27/月），S3 算 30 篇，S4 算每日 1 篇。**任務書寫的是每週 3 篇、每月 12 篇。** 差 2.5 倍。

影響有兩層：

| 層面 | 30 篇/月的結論 | 12 篇/月的實際 |
|---|---|---|
| 月成本 | S2 說 $22-27 | 約 $8 到 $10 |
| 工程投資攤提 | 每篇省 $0.05 → 月省 $1.5 | 月省 $0.6 |
| 統計樣本累積 | 90 天 90 篇 | **90 天 36 篇** |

第三列最痛。S7 §3.1 的樣本量表在 12 篇/月下要重算：偵測 +50% 效果需 20 篇（約 1.7 個月），+30% 需 56 篇（**約 4.7 個月，超出 90 天窗口**）。S2 的 hook A/B 配對檢定 n=30 需要 **2.5 個月**而非 30 天。

**所有既有設計文件裡的「N 天後有結論」都要乘 2.5。** 這件事要在動工前跟 Jesse 對齊，否則 90 天後所有實驗都會是「樣本不足」。

## 0.2 在 12 篇/月的節奏下，prompt caching 幾乎沒有省錢效果

[驗證，claude-api 官方文件] Prompt cache TTL 只有 5 分鐘（預設）或 1 小時（2 倍寫入成本）。每 2 到 3 天發一篇的節奏，**兩次撰稿之間 cache 必然過期**。

| 快取情境 | 是否命中 | 說明 |
|---|---|---|
| 撰稿 → 自審改寫（同模型、5 分鐘內） | ✅ 命中 | 唯一穩定命中的一處 |
| 前一篇撰稿 → 後一篇撰稿（間隔 2-3 天） | ❌ 過期 | 5m 和 1h TTL 都撐不到 |
| S1 粗篩（Haiku）→ S2 精排（Opus） | ❌ 不共用 | cache 是 model-scoped |
| 同一天連跑 3 篇（批次日） | ✅ 命中 2 篇 | 需改生產節奏 |

**推論：S2 與 S3 裡「掛 prompt cache 省 15%」的估算在這個量級不成立，實際省下不到 $0.5/月。不要為了快取做架構改動。**

但「批次日生產」（例如週日一次產 3 篇）有**獨立於成本的價值**：Jesse 一次進入審稿狀態處理 3 篇，比分 3 天各進入一次省的分鐘數遠大於快取省的錢。這條該做，但理由是北極星，不是成本。

**另一個快取細節 S3 算錯了** [驗證]：Haiku 4.5 的最小可快取前綴是 **4,096 tokens**（Opus 5 是 512、Sonnet 5 是 1,024）。S3 §5.2 寫「S1 粗篩 Haiku + rubric 800 快取」，800 tokens 低於門檻，**會靜默不快取，不報錯**。這一項的省錢是零。

## 0.3 現況成本基線查不到，$15 的組成不明

我把 repo 全查過，`data/` 沒有任何成本紀錄檔，HANDOFF 沒有帳單數字。我用 token 反推的 Anthropic API 現況是 **約 $3.1/月**，跟「$15 級距」對不上。

# 2. 模型選型原則

## 2.1 六條判準，依序問

不是「這個任務難不難」，而是這六個問題，**由上而下第一個 yes 就決定執行者**：

| 順序 | 判準 | 若 yes | 理由 |
|---|---|---|---|
| **1** | 輸出有沒有唯一正確答案？（數學、查表、API 對帳、時戳比較、集合運算） | **純程式** | 花錢買一個「大部分時候對」的答案，去換一個「一定對」的答案，是負收益 |
| **2** | 判準能不能窮舉成詞表或門檻？（禁詞、長度、比例、黑名單） | **純程式** | 可版控、可審計、可複驗、執行 <1 秒。且能寫進前端讓回饋變 0 秒 |
| **3** | 是不是純抽取 / 分類 / 格式填充，且**錯了下游機械檢查會抓到**？ | **Haiku 4.5** | 有安全網就不需要買保險。strict structured outputs 讓 schema 錯不了 |
| **4** | 需不需要**語意比對**或**只回報事實**（不做決定）？ | **Sonnet 5** | 「這段 abstract 支不支持這句話」是比對；「決定要不要 block」是規則，交給 Python |
| **5** | 需不需要**跨項相對排序**或**整體判斷**？ | **Sonnet 5**（一般）<br>**Opus 5**（若同時是品質瓶頸） | 相對排序必須一次看全部。單獨看一張圖判斷不了它在第 5 張好不好 |
| **6** | 是不是**創作**（沒有標準答案）**且直接決定成效**？ | **Opus 5** | 這是唯一該付 Opus 溢價的情境 |

## 3.1 估算方法

**每一個數字的算法**，可以複驗：

```
單次成本 = (input_tokens × 單價_in + output_tokens × 單價_out) / 1,000,000
output_tokens = text_tokens + thinking_tokens   ← Opus 5 兩者同價 $25/M
vision input = ⌈寬/28⌉ × ⌈高/28⌉ visual tokens  [驗證，官方公式]
  4:5 @512px = 410×512 → 15×19 = 285 tokens/張
  4:5 @256px = 205×256 → 8×10 = 80 tokens/張
```

# 4. 成本控制

## 4.1 閘門設計：內容雜湊分離（最重要的一條）

**問題**：Jesse 改一句文案，不該重跑整篇 vision 策展。現況沒有任何機制阻止這件事。

**做法**：三個獨立雜湊，寫進 `posts.json`，每個下游任務只在自己的上游雜湊變動時才重跑。

```json
"hashes": {
  "copy_hash":    "sha256(所有 slide 的 display_copy + heading + caption)",
  "visual_hash":  "sha256(所有 slide 的 chosen_cid 排序後串接)",
  "render_hash":  "sha256(copy_hash + visual_hash + template_id + render_config)"
}
```

**觸發矩陣**

| 變動 | 重跑什麼 | 不重跑什麼 | 省下 |
|---|---|---|---|
| 只改文案（`copy_hash` 變） | 14 條機械檢查（本機 $0）+ **只有變動 slide 的 claim** 重跑 L1/L2 | S1 粗篩、**S2 精排**、生圖 | **$0.057/次** |
| 只換底圖（`visual_hash` 變） | R1-R8 執法（$0）+ 節奏檢查（$0）+ 總檢 | 撰稿、查證、S1 粗篩 | **$0.276/次** |
| 換模板（`template_id` 變） | 渲染 + 排版回歸 + 總檢 | 撰稿、查證、策展 | $0.329/次 |
| 重出成品（`render_hash` 變） | 總檢 | 全部上游 | $0.315/次 |

**claim 級增量查證**：`claims[]` 每條帶 `slide_n` 與 `text_hash`。改文案時只重跑 hash 變了的那幾條，不是整篇 12 條。實務上 Jesse 改一句通常只動 1 條 claim，L2 判讀成本從 $0.033 降到約 $0.005。

[推理] 以 `copy_edits.json` 現有紀錄估，Jesse 平均每篇改 3 到 5 處。**沒有這個閘門，一篇的實際成本會是估算的 2 到 3 倍。這是全文最高投報比的一條工程。**

## 4.2 快取策略（誠實版）

**結論先講：在 12 篇/月的節奏下，prompt caching 省不到 $0.5/月，不要為它做架構改動。**

理由見 §0.2。三處值得掛快取的地方，但理由不是省錢：

| 位置 | 命中條件 | 月省 | 真正的理由 |
|---|---|---|---|
| 撰稿 → 自審改寫 | 同模型 5 分鐘內，穩定命中 | ~$0.15 | 順手，不掛白不掛 |
| 批次日連跑 3 篇 | 需改生產節奏 | ~$0.28 | **真正理由是 Jesse 一次進入審稿狀態省的分鐘數** |
| 策展 rubric | Opus 5 最小 512 tokens [驗證]，2,000 tokens 的 rubric 可快取 | ~$0.05 | 順手 |

**明確不要做的**：Haiku 粗篩的 rubric 快取。[驗證] Haiku 4.5 最小可快取前綴是 **4,096 tokens**，S3 設計的 800 tokens rubric 低於門檻，**會靜默不快取且不報錯**。掛了只是自我感覺良好。

**若未來拉到 30 篇/月且改成批次日生產，快取的價值會從 $0.5 升到約 $2.5/月，那時再重新評估。**

## 4.3 其他四個槓桿（依效果排序）

| # | 槓桿 | 月省 | 說明 |
|---|---|---|---|
| 1 | **合併 curate 呼叫（9→1）** | **$1.04** | 省掉 8 份重複 rubric。不依賴快取，純架構改動，V23-A 該最先做 |
| 2 | **Batch API**（撰稿 + 策展，前一晚跑） | **$1.78** | [驗證] 50% 折扣，多數 1 小時內完成，上限 24 小時。09:00 產、下午審的節奏可以吸收。**注意 [驗證]：Batch 不接受 `fallbacks` 參數，且含 web_search 的 batch 會被節流** |
| 3 | **素材庫命中** | 遞增，長期最大 | person role 命中率預期高（Attached/Aziz 已重打三次）。直接減少候選張數 = 直接減少 vision 成本 |
| 4 | **256px 粗篩** | 已計入 | 80 tok vs 285 tok，差 3.5 倍 |

## 4.4 監控：`cost_log.jsonl`（Day 1 就要有）

**每一次 API 呼叫**都 append 一行。沒有這個，§3.5 的最大變數永遠估不準。

```json
{"ts":"2026-08-14T09:02:11+08:00","post":"20260814-xxx","task":"T2.2_write",
 "model":"claude-opus-5","effort":"high","thinking":"adaptive",
 "usage":{"input_tokens":9412,"output_tokens":7108,
          "cache_creation_input_tokens":0,"cache_read_input_tokens":0},
 "thinking_tokens_est":3900,"cost_usd":0.2248,
 "trigger":"copy_hash_changed","retry_count":0}
```

**六個監控指標**，週報自動算：

| 指標 | 算法 | 紅線 | 為什麼是這條 |
|---|---|---|---|
| **每篇總成本中位數** | `cost_log` 按 post 彙總 | > $0.90 | 估算是 $0.55，超過 1.6 倍代表重跑失控 |
| **重跑倍率** | 實際呼叫數 / 理論最小呼叫數 | > 1.8× | 直接檢驗 §4.1 閘門有沒有生效 |
| **thinking token 佔比** | `thinking_est / output_tokens` | > 70% | 超過代表 prompt 太複雜或 effort 太高 |
| **cache 讀取率** | `cache_read / (cache_read + input)` | 記錄不設線 | 12 篇/月本來就低，設線會誤導 |
| **每篇 vision tokens** | 圖片 token 總和 | > 12,000 | 候選數失控（實測最大 64 張 = 18,240） |
| **成本 / Jesse 分鐘** | 月成本 / 月分鐘數 | 記錄不設線 | 這才是真正該優化的比值 |

**最後一項是這套監控的重點。** $8/月的絕對值沒有意義，「花 $8 換 Jesse 每月省 3 小時」才有意義。如果某個優化省了 $2 但讓 Jesse 多花 20 分鐘，那是虧的。

# 5. 人審關卡設計

## 5.1 設計原則：關卡不是變少，是只在有風險時才打斷

Jesse 一人，關卡總數必須有硬上限。但「產出需要被審視」也是真的。解法是把關卡從「逐項確認」改成「例外處理」：**系統先給結論，Jesse 只推翻結論。**

## 5.2 關卡總數上限

**每篇貼文最多 2 個必經人審關卡 + 1 個條件觸發關卡 + 每週 1 個系統級關卡。**

| # | 關卡 | 時機 | 必經? | 時間預算 | Jesse 的動作 |
|---|---|---|---|---|---|
| **G1** | **雷達放行** | 每日（批次） | 必經 | **3 分鐘 / 7 張卡** | 放行 / 丟棄 / 改角度 / 進口袋 + 必填放行理由（單選） |
| **G2** | **審稿台** | 每篇 | 必經 | **目標 5 分鐘 / 篇**（現況 [待查]） | 掃 9 張成品膠捲 → 處理 0-3 個待決項 → 核准 |
| **G3** | 排程 | 每篇 | **否，閘門過就自動落 slot** | 0 分鐘 | 只有 H1-H8 硬擋或 R1-R6 違規時才需要人 |
| **G4** | 法遵例外 | 條件觸發 | 條件 | 1 分鐘 | 見 §5.4 |
| **W1** | `learnings.json` diff | 每週 | 必經 | **1 分鐘 / 週** | 看 0-3 條規則變更，核准才寫入 prompt |

**每月人審總時間預算**：G1 3 分 × 30 日 + G2 5 分 × 12 篇 + W1 1 分 × 4 週 = **154 分鐘/月，約 2.6 小時。**

**現況 [驗證]**：`awaiting_review` 積壓 14 篇，且單篇耗時完全沒有量測。所以上面的預算是**目標值不是承諾**。第一件事是埋 `effort_log.json` 量出基線，否則無從判斷改善。

## 5.3 什麼必須人審，什麼自動放行

判準是**四個維度**，命中任一就必須人審：

| 維度 | 定義 | 例子 |
|---|---|---|
| **不可逆** | 做了收不回來 | IG 發佈、ClickUp 建卡、Drive 歸檔覆蓋 |
| **對外** | 讀者看得到 | 文案、成品圖、caption、hashtag |
| **法遵** | 有授權或事實風險 | 引用出處、劇照使用、產品金額、真人肖像 |
| **品味** | 沒有機器判準，且錯了會傷品牌 | hook 的自我辨識度、視覺的 AI 味、語感 |

**對照表**

| 決策 | 維度命中 | 處置 | 判準 |
|---|---|---|---|
| 靈感卡放行 | 品味 | **人審**（G1） | rubric 7 項只有 3 項是機器算的，第 5「自我辨識」與第 6「會轉給特定人」機器判不了 |
| hook 是否空洞 | 品味 | **機器先擋，人審終判** | H1/H3 是 block 級硬擋（`sync_console.py` 加 40 行），過了才進人眼 |
| 文案禁詞 / 長度 / CTA 逐字 | 無（可窮舉） | **自動 block** | 14 條規則，錯不了 |
| 引用是否有出處 | 法遵 | **機器對帳 + 人審 `unsupported`** | L1 matched 自動過，`unsupported` 硬擋等 Jesse 一鍵採納改寫 |
| 引用詮釋是否正確 | 法遵 | **標「已驗到出處層」，不給綠勾** | [驗證] abstract 是天花板，驗不到詮釋。**給綠勾比不驗更危險** |
| 圖片硬規則（R1/R2/R3/R4/R8） | 無 | **自動淘汰** | 主體重複、role 不符、分數線、浮水印、同源 |
| 圖片軟旗標（R5/R6/R7） | 品味 | **人審**（G2 內，Tab 跳旗標） | 明暗、構圖、人物比例是美學判斷 |
| 生成圖 G1/G2/G6/G7 | 無 | **自動退並重生** | 有文字、臉>2、撞圖、書名不符 |
| 生成圖 G3/G4/G5 | 品味 | **標紅進人眼，預設不選中** | 大臉、有手、琥珀味 |
| 排程 slot | 無 | **自動落 slot** | H1-H8 全過就磁吸，不需要人 |
| 節奏違規 R1-R6 | 品味 | **警告可覆寫，需勾選確認** | 型別失衡是判斷不是錯誤 |
| `learnings.json` 進 prompt | 品味 | **人審**（W1） | 這是系統的自我修改，不能無人值守 |
| 劇照使用 | 法遵 | **人審**（G4） | 見 §5.4 |
| 產品金額 / 服務規則 | 法遵 | **自動 block，逐字比對** | `lava-product-context` 金額表，完全確定 |

## 5.4 條件觸發關卡（G4）

只在四種情況打斷，其餘全部不出現：

| 觸發 | Jesse 看到什麼 | 為什麼要人 |
|---|---|---|
| 貼文含 TMDB / 劇照素材 | 「本篇使用 3 張作品劇照。TMDB 商業使用需授權（$149/月）。目前為引用式使用 + 出處標注」+ [仍要用] [換素材] | S3 §1.6 的法遵紅線，且與 §1.2 的視覺衝突直接相關 |
| 貼文含真人肖像且非 Wikimedia CC/PD | 授權來源與標注預覽 | 肖像權 |
| 生成圖首次進入已發佈流程 | 「這是第一則含 AI 生成圖的貼文，Meta 可能自動加 AI info 標籤」 | S4 §9 的 SynthID 未驗證風險，一次性 |
| `unsupported` claim 且 Jesse 選擇忽略 | 「你正在發佈一則查無出處的主張」+ 二次確認 | 這是唯一該有二次確認的地方 |

## 5.5 三個讓關卡不疲乏的機制

| 機制 | 做法 | 效果 |
|---|---|---|
| **影子模式** | 任何新檢查規則上線後**先跑兩週只記錄不阻擋**，統計 Jesse 推翻率。只有推翻率 <10% 才升級成硬擋 | 防止新規則把審稿時間反向拉長 |
| **推翻率長在規則旁邊** | 規則面板每條規則顯示「近 30 天觸發 N 次，Jesse 推翻 M 次」 | 推翻率是調閾值的唯一依據，必須跟規則同畫面 |
| **反過度自信** | 任何 AI 分數（病毒分、策展分、hook 分）**一律不以裸數字呈現**，改「通過 4/6 項」+ 未通過清單 | 顯示 8.5 分會讓 Jesse 把它讀成預測力，而它從未校準過 |

# 7. 我這份設計最弱的三環

## 7.1 最弱：整套成本模型建立在一個我拍出來的 thinking token 數

撰稿佔 Anthropic 預算的 46%，而它的 66% 是 thinking token，而我對 thinking token 的估計（4,000/篇）**沒有任何依據**。[驗證] Opus 5 的 `display` 預設 `omitted`，thinking 內容拿不到但照樣按 $25/M 計費，所以連事後回推都困難，只能靠 `usage.output_tokens` 減去 text token 反推。

若實際是 12,000 tokens，月成本從 $6.35 變 $8.75（+38%）；若是 1,500，變 $4.85（−24%）。**這個 ±40% 的不確定性大於本方案所有優化加起來的效果。**

**處置**：`cost_log.jsonl` Day 1 上線，先跑 5 篇再談任何數字。在那之前不對 Jesse 承諾月成本。

## 7.2 次弱：12 篇/月的產能讓所有「工程投資 → 省錢」的論證都變弱

我花了 §4 整節設計快取、閘門、Batch，加總省下約 $3/月。**一個中階工程師一小時的機會成本就超過這個數字。**

誠實講：**在 12 篇/月的量級，成本優化不值得做，除非它同時改善 Jesse 的分鐘數。**

用這個標準重新檢視 §4：
