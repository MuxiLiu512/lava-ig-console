## 0. 一句話結論

現行 finalize 環節的根本問題不是「版型只有一種」，是**「節奏」這件事被交給了一個不穩定的裁判**。

節奏是可計算的：明度、色溫、版型序列、文字覆蓋率、感知雜湊，全部零 AI、本機 PIL、單篇 1 秒內算完。把它從 WF15 vision 的主觀判斷改成渲染當下的確定性計算，同時解掉三件事：節奏停滯有了可執行的修法、總檢判準不穩收斂了一半、vision 只剩下它真正不可替代的一件事（辨識「這是不是同一個具名主體」）。

版型庫是這條主張的執行工具，不是目的。

**另外，我在讀 code 時發現一個既存缺陷必須先講**：`check_typography.py:54` 用 `W*0.043` 檢查封面主標，但引擎 `render_cover` 實際渲染用的是 `W*0.075`（超寬時以 0.92 逐級縮，下限 `W*0.05`）**[驗證]**。字級差 57%，斷行點完全不同。副標同樣不符（檢查 `max_w=W*0.78`，引擎 `W*0.89`；引擎另有 1.0 到 0.68 的縮字迴圈，檢查固定用 1.0）。內文張也一樣（引擎 1.0 到 0.75 縮字，檢查固定 1.0）。

也就是說，`self-check.md` A8 宣稱「驗的是實際會印出來的版本」，在封面上是不成立的。A3／A5 修的正是封面詞中斷行，而它的回歸驗證跑在一個不存在的字級上。這是第 5 節的第一項，也是我建議的第一個施工項。

## 1. 版型庫

### 1.1 前提：先把引擎改成版型登錄制，且預設行為不變

現行 `render_post_v5.main()` 只有兩條分支：`i == 1 or role == "Hook"` 走 `render_cover`，其餘走 `render_content` **[驗證]**。改造方式：

```python
TEMPLATES = {"full_bleed_bottom": T1, "top_band": T2, ...}
tpl = TEMPLATES.get(s.get("template") or _auto_template(s), T1)
```

`slide.template` 缺值時 `_auto_template()` 回傳 `full_bleed_bottom`，行為與今天逐位元相同。**這是「改造不能停擺」的具體做法：新版型逐個進 registry，沒指定版型的稿一律走舊路徑。**

每個版型必須實作兩個函式，這是硬約束：

| 函式 | 用途 | 為什麼是硬約束 |
|---|---|---|
| `render(slide, bg, out, ctx)` | 畫圖 | |
| `text_slots(slide, ctx) -> [{text, font_path, size_px, max_w, wrap_mode, color}]` | 宣告這個版型會印出哪些文字、用什麼字級與寬度 | `check_typography` 與 render manifest 都讀這一份。**沒有 `text_slots` 的版型不得進 registry**，否則新版型一上線，排版回歸檢查就對它全盲 |

所有版型共用既有 primitive：`draw_footer`、`logo_img`、`draw_credit`、`parse_highlight`、`wrap_segments`、`wrap_semantic`、`strip_line_ends`、`dyn_overlay`、`top_scrim`。品牌一致性靠共用元件保證，不靠人記得。

## 2. 視覺節奏規則

### 2.1 五個可算的量

每張成品渲染完當下計算，寫入 `posts.json` 的 post 層（**不要寫進 `slides[]`，refeed 會沖掉，這是 self-check E1 的教訓** **[驗證]**）：

| 量 | 定義 | 實作 |
|---|---|---|
| `L` 明度 | 成品上緣 0 到 0.55H 區域的 L 通道中位數（0 到 255）。取上半是因為下半永遠被遮罩壓暗，帶不了資訊 | `im.convert("L").crop(...)`，`statistics.median` |
| `warm` 暖色比 | HSV 中 S>0.2 的像素裡，H 落在 10° 到 50° 的占比 | 沿用 S4 的 G5 定義，判準一致 |
| `text_ratio` | 文字 bbox 面積和／畫布面積 | 排版當下已知每行位置與寬度，直接累加，不需 OCR |
| `tpl` | 版型 ID | 資料欄位 |
| `dhash` | 8×8 差分感知雜湊 | PIL 15 行，零依賴 |

### 2.2 八條規則（全部可機器驗證）

| 代碼 | 規則 | 判準 | 嚴重度 |
|---|---|---|---|
| R1 | 版型不得連續重複三張 | 存在 i 使 `tpl[i]==tpl[i+1]==tpl[i+2]` | block |
| R2 | 版型多樣度 | 9 張需 ≥4 種；7 張以下需 ≥3 種 | block |
| R3 | 明暗有起伏 | `max(L)-min(L) ≥ 25` **且** L 序列穿越中位線的方向改變次數 ≥2 | warn |
| R4 | 亮張下限 | `L > 110` 的張數 ≥2（把 `style-notes.md`「亮色調至少 2 張」變成可算的定義） | warn |
| R5 | 暖色上限 | `warm > 0.45` 的張數 ≤2（對齊「琥珀感最多 2 張」） | warn |
| R6 | 相鄰不得雙同 | 不得連續三張同時滿足 `|Δwarm| < 0.05` 且 `|ΔL| < 8`。這就是「像翻同一份簡報」的量化定義 | block |
| R7 | 呼吸節奏 | 至少一張 `text_ratio < 0.08`（喘息張）且至少一張 `> 0.18`（資訊張） | warn |
| R8 | 不得重圖 | 相鄰兩張 dHash hamming ≥10；全篇任兩張 ≥6 | block |

實作為 `scripts/check_rhythm.py`，掛哨兵每輪，跟 `check_typography.py` 同一個位置。成本 $0，單篇 <1 秒。

### 2.3 為什麼這件事要從 vision 手上拿回來

WF15 判「節奏停滯」有三個結構性問題：它不可重現、它不能告訴你要改哪一張、它會為了「有東西可講」而在沒問題時也產出評語。上面八條規則反過來：確定性、指名到張、可以在渲染當下就自動換版型重出，而不是等人看到評語再手動處理。

**同時這解掉問題 3 的一半**：把主觀項從 WF15 的問題清單裡移除，等於減少了污染同一次回應中客觀項的雜訊源（見 3.1）。

### 2.4 門檻值的誠實聲明

`L>110`、`warm>0.45`、`hamming 10`、`ΔL<8` 全部是我拍的 **[推理]**，跟 S4 的 G1 到 G7 一樣沒有校準集。

差別是**這次可以今天就有基線**：`docs/finals/` 下已有既往成品，跑一次就能得到現有分布。做法：先 log-only 跑兩週，記錄每篇的五個量與現行 WF15 的節奏評語，用「WF15 說停滯的篇」對照 R3／R6 的實際值來定線。上線第一週不開 block。

## 3. 成篇總檢判準修正

### 3.1 先歸因：為什麼同一篇兩次判定不同

現行 `_post_qa()` 把 9 張圖一次送 n8n webhook，讓 vision 同時回答撞主體、浮水印、可讀性、出處異常、節奏五個維度 **[驗證，`sync_console.py:1102`]**。n8n 端 prompt 我看不到 **[待查]**，但不穩定的來源可以從輸入端結構推出四項 **[推理]**：

1. **一次問五個維度**，其中「節奏」是開放主觀項。開放項會拉高整體輸出的溫度感，模型傾向填滿清單。
2. **關係型判斷（撞主體）沒有中介表徵**。模型直接輸出「第 2、5 張重複」這個結論，沒有先說出重複的是什麼。結論層的採樣變異遠大於命名層。
3. **輸出未被 schema 約束**，`severity` 是模型自由選的字串。
4. 圖片壓縮參數雖固定（820×1025／q82），但**沒有記錄輸入 hash**，所以「兩次不同」到底是輸入變了還是模型變了，現在無法歸因。

### 3.2 修正一：把能算的全部拿走，vision 只留一件事

| 現行由 vision 判 | 改由 | 理由 |
|---|---|---|
| 節奏停滯 | `check_rhythm.py`（第 2 節） | 確定性、可指名到張 |
| 文字不可讀（B3） | **引擎內建對比度計算**（見 3.4） | 引擎知道每個字的座標與顏色，算得比看得準 |
| 出處標示異常（B4） | 已是正則判斷 | `sync_console.py:836` 已在做 |
| 浮水印（B2） | vision，但改成**單張二元問題＋sha256 快取** | 視覺特徵明確，適合 Haiku |
| **主體重複（B1）** | **vision，兩階段（見 3.3）** | 這是唯一需要世界知識的判斷 |

### 3.3 修正二：主體重複改成「先命名，再比對名字」

**階段 A（零 AI，先跑）**：每張成品的底圖已經帶 provenance：`source_kind`、`src_key`（同源去重鍵）、`source_label` **[驗證，`forage_shots.py` 與 `sync_console.py:820-850`]**。

```
同 src_key 或同 source_label → same_subject，直接 block，100% 穩定
```

Aziz 事件（三張同一本書封）在這一層就會被抓到，因為書封的 `src_key` 相同。這件事根本不需要送 vision。

**階段 B（vision，只在 A 沒抓到且可疑時觸發）**：候選對的篩選條件是 `dHash hamming < 18` 或 `role` 相同。典型每篇 0 到 2 對。只送這一對，問一個二元問題。

**判準的操作型定義寫死在 prompt 裡，並強制輸出結構：**

```json
{"pair":[2,5],
 "subject_a":"Aziz Ansari 本人（同一張 press 照的不同裁切）",
 "subject_b":"Aziz Ansari 本人（TED 舞台）",
 "same_subject": true,
 "why":"同一位具名人物"}
```

**核心機制：只有當模型自己填出的 `subject_a` 與 `subject_b` 指向同一個具名個體時，才允許判 block。** 這把「重複與否」這個關係判斷，拆成「命名 → 比對名字」兩步。命名比關係判斷穩定得多，因為它有外部錨點（人名、書名）。

同時這直接解掉「同類型誤判成同主體」：

| 情況 | subject_a | subject_b | 判定 |
|---|---|---|---|
| 兩張都是 Aziz | 「Aziz Ansari 本人」 | 「Aziz Ansari 本人」 | **block** |
| 兩張不同人的劇照 | 「《愛在黎明破曉時》Jesse」 | 「《正常人》Marianne」 | **pass**（不是 warn，這是正常的內容多樣性） |
| 兩張都是無名情境照 | 「不可辨識的女性背影」 | 「不可辨識的街景」 | **pass** |
| 兩張同一本書不同角度 | 「《Modern Romance》書封」 | 「《Modern Romance》書封」 | **block** |

「同類型」在這個結構下**根本不會產生 block 候選**，因為兩個 subject 字串本來就不同。不需要多一條「同類型降級為 warn」的規則，判準本身就把它排除了。

### 3.4 修正三：文字可讀性改成算的，而且會自動修

引擎在疊字前已經知道：每一行的 bbox、文字顏色、遮罩後的底圖。所以可以直接算 WCAG 對比度。

我算了現行三種文字色的相對亮度 **[推理，依 WCAG 2.x sRGB 公式手算]**：

| 顏色 | 值 | 相對亮度 |
|---|---|---|
| 白 | `#FFFFFF` | 1.000 |
| 重點黃 `【】` | `#FAD228` | 0.666 |
| **超級重點橘 `〖〗`** | `#E84224` | **0.213** |

要達到 4.5:1，背景相對亮度須 ≤ `(L_fg+0.05)/4.5 - 0.05`：

- 白字：背景可到 0.183（sRGB 約 118/255），幾乎不會失敗
- 黃字：背景可到 0.109（sRGB 約 92/255），安全
- **橘字：背景須 ≤ 0.0084，換算 sRGB 約 23/255**

而遮罩最深 `MAX_ALPHA=198` 的合成式是 `out = img*0.224 + 3.9` **[驗證，`dyn_overlay` 與 `MAX_ALPHA=198`]**，所以底圖像素必須 **暗於 84/255**，橘字才達得到 4.5:1。

**結論：`〖〗` 超級重點橘在中亮底圖上是不合格的，而且現行 `stroke_fill=color` 的假粗體只會加粗，不會改善對比。** 這是一個沒有人發現的既存問題，因為肉眼看橘色在暗背景上「還算看得到」。

三個修法，建議取第二個：

1. 限制 `〖〗` 只能出現在保證暗的區域（脆弱，依賴底圖）
2. **定義一組「文字安全色」**：文字用途的橘改為 `#F5784F`（相對亮度 0.334，同樣底圖下對比約 5.9:1），`#E84224` 保留給橘槓等實色元件。品牌辨識度不受影響，因為橘槓才是識別元素
3. 橘字加 2px 深色描邊（會改變字的觀感，且與現行假粗體衝突）

**自動修機制**：渲染時對每行算 `contrast_min`，低於 4.5 就在該行 bbox 範圍內把遮罩局部補到達標（`dyn_overlay` 加一個 per-row 補償項），再重算。補到 alpha 上限仍不足才 block。**這是修好而不是報錯**，直接省掉一次人的介入。

### 3.5 修正四：穩定性工程（四件事）

1. `temperature=0` ＋ structured outputs 強制 schema
2. **輸入 hash 記錄**：把送出的 9 張壓縮圖的 sha256 寫進 `qa` 紀錄。這樣「兩次判定不同」才能歸因
3. **block 級一致性閘門**：block 判定必須連跑 2 次結果一致才生效；不一致則降級為 warn 並標「判定不穩」。因為多數篇沒有 block 候選，期望成本增加很小
4. **`data/archive/postqa.jsonl`**：存每次總檢的 input sha、prompt 版本、raw response、最終判定。**現況只把最後一次結果覆寫進 `posts.json.qa`，歷史全丟 [驗證]，所以「判準改了有沒有變穩」這個問題結構上無法回答。這是目前最大的盲點。**

**可執行的驗收條件**：拿現有 10 篇成品，同一篇連跑 3 次，計算 block 集合的 Jaccard 相似度。現況先量基線，改版後目標 ≥0.9。

## 4. 封面策略

### 4.1 拆解 heavenraven 的 Tom Holland 封面

依 Jesse 提供的描述拆解 **[推理，我沒看到原圖，以下是從文字描述反推的結構]**：

| 原則 | 內容 | 可否遷移到 Lava |
|---|---|---|
| P1 主體是**具名人物的臉** | 讀者 0.3 秒內知道這是誰，辨識成本為零 | **有條件**，見 4.2 |
| P2 標題是**斷言**不是問句 | 「他想要，他得到」是陳述，不是「你有沒有發現」 | 可，且是 Lava 最該學的一條 |
| P3 **三拍結構** | 事實／事實／評價。前兩拍壓縮，第三拍給態度（「太會向宇宙下訂單」） | 可，且可機器驗證 |
| P4 資訊缺口**具體且可兌現** | 承諾的是一串證據（他說了什麼、幾年後成真），不是抽象概念 | 可，這正是 S2 的 H3 缺口關閉 |
| P5 視覺是**真實劇照與訪談截圖** | 不是生成圖，不是設計卡。真實素材本身就是隱性背書 | 可，`forage_shots.py` 的 SHOT 路線已對齊 |
| P6 **不對讀者說話** | 沒有「你」，讀者是旁觀者不是被說教者 | 可，且與 Lava 現行「欸，你有沒有發現」正好相反 |

**必須誠實標出的遷移風險**：27.7k 讚是該帳號的成績，不是版式的成績。**[待查] @heavenravenofficial 追蹤基數未知**。更關鍵的是 P1：Tom Holland 自帶搜尋量，Lava 若選一個台灣讀者不認識的人物，P1 的效力歸零，剩下的只是一張陌生人的臉，那比情境照更糟。

**所以人物型封面的第一道檢查不是「這人有沒有好照片」，是「這人在台灣有沒有辨識度」。**

可機器判定的代理指標：中文維基百科條目存在，且該條目近 30 天瀏覽數 ≥ 門檻。Wikimedia Pageviews REST API 免費無金鑰 **[驗證，Wikimedia REST API 為公開免費端點]**。門檻先設 3000 次／30 天，log-only 校準。

### 4.2 hero／collage 的選擇機制

現況：`forage_shots.py:676` 對最小編號 slide 同時產 `a`（單張 hero）與 `b-collage`（組圖），操控室並列讓 Jesse 挑 **[驗證]**。問題不是「沒有機制」，是**選擇的軸錯了**：兩版並列隱含「挑好看的」，但這兩者的差別根本不是好不好看。

**核心主張：組圖不是另一種好看的版面，它是一個資訊承諾。**

單張 hero 承諾的是「這裡有一個主體，我要講他」。組圖承諾的是「這裡有很多例子」。把組圖用在單一主體的內容上，讀者滑進去只看到一件事，這是失約，跟空洞 hook 是同一類錯誤。

**決策表（機器判定，人只覆寫）**：

| 條件（全部可機器驗證） | 封面版式 | 依據 |
|---|---|---|
| 有具名人物 ＋ 維基瀏覽數過門檻 ＋ 有 ≥1 張該人物高質感真實照（`source_kind` 非 SHOT-internal） | `hero_person` | P1，辨識成本最低 |
| 證據素材 `src_key` 互異 ≥3 | `collage_evidence`（T7） | 資訊承諾與清單型內容一致 |
| 抽象概念，無具名主體，mood 候選最高分 ≥6 | `hero_mood` | 概念沒有臉，硬找人臉會產生 stock 感 |
| 抽象概念，且 mood 候選最高分 <6 | `typographic`（T8 變體，純字大卡） | 沒好圖就不用圖，這比用一張爛圖強 |
| `topic_type` = 服務介紹 | `brand_solid` | 不借外部圖的權威 |

**這條規則直接刪掉一次每篇必發生的無依據決策**，對北極星（每篇消耗 Jesse 幾分鐘）是直接收益。人的覆寫保留為一顆按鈕，覆寫時記錄原因，累積 20 次後回頭看規則哪裡不對。

### 4.3 封面文案結構規則（從 P2 到 P6 導出，可機器驗證）

接在 S2 的 H1 到 H6 之後：

| 代碼 | 檢查 | 判準 | 嚴重度 |
|---|---|---|---|
| C1 | 三拍結構 | 主標切成 2 到 3 個短句，每句 ≤10 字，總長 12 到 24 字 | warn |
| C2 | 至少一句斷言 | 主標非全為問句（現行清一色問句開場，見 A1／A2） | warn |
| C3 | 第三人稱優先 | 主標出現「你／妳」時，須同時存在第三方具名主體，否則 warn。純第二人稱說教是現行模板感的主要來源 | warn |
| C4 | 封面版式與內容一致 | `collage_evidence` 時，內頁必須有 ≥3 個互異例證（用 `src_key` 互異數驗） | **block** |

C4 是把「資訊承諾」變成資料結構驗證，跟 S2 的 H3（缺口關閉）是同一個手法。

## 5. 品質驗證補強：現有機制的盲區

現有五道：缺字備援、語意斷行、行尾標點清除、`check_typography`、WF15 總檢。以下九個盲區按嚴重度排序。

**盲區 1（最嚴重）：`check_typography` 驗的字級與引擎實際不符。**
`check_typography.py:54` 封面主標用 `W*0.043`，引擎 `render_cover` 用 `W*0.075`（含 0.92 逐級縮字）；副標 `max_w` 檢查用 `W*0.78`，引擎用 `W*0.89`；內文張引擎有 1.0 到 0.75 的縮字迴圈，檢查固定用 1.0 **[驗證，逐行比對兩檔]**。字級不同，斷行點就不同，所以 A3／A5 修的封面詞中斷行，其回歸驗證跑在一個不存在的版本上。
**補法**：引擎渲染時輸出 `data/render_manifest/{pid}.json`，記錄每張最終選定的字級、`max_w`、以及**實際印出的每一行**。`check_typography` 改讀 manifest 而不是重算。這同時讓 `rendered_lines`（E1）與檢查共用同一份真相，不再有兩套斷行邏輯。**這是第一個該做的項目。**

**盲區 2：文字疊在什麼底色上，完全沒有檢查。**
見 3.4。橘字在中亮底圖上不達 4.5:1，現行機制完全看不到。補法同 3.4（對比度計算 ＋ 局部遮罩自動補償 ＋ 文字安全色）。

**盲區 3：沒有像素級回歸。**
改引擎後，不知道哪幾張變了、變在哪。`data/golden/` 目錄已存在但未用於此。
**補法**：固定 3 篇稿 ＋ 固定底圖 ＋ 固定文案為 golden set，渲染後與 baseline PNG 逐像素比較（`ImageChops.difference`），diff 面積比 >0.5% 且未在 commit message 宣告 → 擋下。零成本、零依賴。這條在版型庫逐個上線時是必需品，否則新版型很容易碰到共用 primitive 而汙染舊版型。

**盲區 4：沒有「整篇」層的機械檢查。** 由 `check_rhythm.py` 補（第 2 節）。

**盲區 5：總檢歷史不存在。** 由 `postqa.jsonl` 補（3.5）。

**盲區 6：渲染到 IG 之間的漂移沒有量過。**
成品是 1950×2438，IG 動態上限 1080×1350 **[驗證，`style-notes.md` §畫布比例]**。`draw_credit` 的字級是 `W*0.017 = 33px`，縮到 1080 寬後剩約 18px，再經 IG 二次壓縮。**[待查] 現在零樣本**。
**補法**：下載一則已發佈貼文的 IG 版本，量測 credit 行是否仍可辨。30 分鐘可做完，做完才知道要不要把 credit 字級拉到 `W*0.020`。

**盲區 7：缺字備援觸發了，但沒人知道。**
備援字型是 Hiragino Sans GB 或 Arial Unicode，字重與 HarmonyOS Sans TC 不同 **[驗證，`F_FALLBACK`]**。同一行內混用兩種字型時字重會跳動，肉眼看得出來但沒有任何提示。
**補法**：`text_slots` 檢查時統計 `fallback_used`，同一行混用兩種字型 → warn，建議改寫用詞（多半可以換一個同義詞避開）。

**盲區 8：CTA 公版完全不經檢查。**
`render_post_v5.main()` 遇到 `"CTA" in role` 直接 `fit_bg(CTA_STOCK)` 存檔 **[驗證]**。`CTA_STOCK` 路徑走的是「找得到哪個就用哪個」的 fallback 鏈。若檔案損壞或路徑漂移，整批貼文的最後一張會壞掉且無人發現。
**補法**：CTA 圖的 sha256 白名單校驗，不符即 block。三行程式。

**盲區 9：人的標準會漂移。** Jesse 審第 9 篇時的標準與第 1 篇不同。
**補法**：finalize 面板的節奏帶旁邊，固定顯示「上一篇通過的節奏帶」當錨（見第 7 節）。

## 6. 任務配置與 vision 成本控制

### 6.1 分工原則

**確定性的用 Python，需要世界知識的用 vision，且 vision 只回答二元問題。**

| 子任務 | 執行者 | 觸發 | 每篇成本 |
|---|---|---|---|
| 版型指派 | 純規則 Python | 渲染前 | $0 |
| 排版渲染 | `render_post_v6`（PIL） | 哨兵每輪 | $0 |
| 對比度計算 ＋ 遮罩自動補償 | 引擎內建 | 渲染中 | $0 |
| 排版回歸（行級） | `check_typography` 讀 manifest | 渲染後 | $0 |
| 節奏檢查 R1 到 R8 | `check_rhythm.py` | 渲染後 | $0 |
| 主體重複 階段 A | provenance 比對 | 渲染後 | $0 |
| 像素回歸 | golden diff | 引擎改動時 | $0 |
| 浮水印 | **Haiku 4.5**，單張二元，sha256 快取 | 只對未驗證過的新來源圖 | 見 6.2 |
| 主體重複 階段 B | **Sonnet 5**，成對二元 | 只對可疑對（典型 0 到 2 對） | 見 6.2 |

### 6.2 vision 成本

Anthropic 的 vision token 估算式為 `tokens ≈ (寬 × 高) / 750` **[驗證，官方公式]**。

**現況**：9 張 820×1025 → 每張約 1,120 tokens，全篇約 10,080 input tokens。Sonnet 5 $3/M → **約 $0.030/篇**。

**改版後**：

| 項目 | 解析度 | 張數 | tokens | 模型 | 成本 |
|---|---|---|---|---|---|
| 浮水印（僅新來源圖） | 820×1025 | 典型 2 到 3 | 2,240 到 3,360 | Haiku 4.5 $1/M | $0.002 到 $0.003 |
| 主體比對（僅可疑對） | 512×640 | 0 到 4 | 0 到 1,748 | Sonnet 5 $3/M | $0 到 $0.005 |
| block 一致性複跑 | 同上 | 條件觸發 | | | 期望 <$0.002 |

**約 $0.008 到 $0.015/篇**，月 30 篇約 $0.35。

**四條控制手段**：

1. **分流解析度**。浮水印是細筆畫平鋪，520px 時漏檢過 Magnific **[驗證，`sync_console.py:1120` 註解]**，所以維持 820px。主體比對只需辨識「是不是同一個」，512px 足夠，token 降 60%。
2. **sha256 快取**。同一張底圖在不同篇重複使用時不重複付費。素材庫複用率上升後，浮水印檢查的邊際成本趨近 0。
3. **只送可疑對**，不送全篇。
4. **只對 block 候選做一致性複跑**。

### 6.3 一句誠實話

現況 $0.030/篇本來就不貴，月成本影響是雜訊。**所以這次改動的理由不是省錢，是讓每一塊錢買到的是可歸因、可重現的判定。** 不要用成本當作說服理由，那會讓人以為這是個優化題，它其實是個正確性題。

4. **不顯示任何分數。** 沿用 UIUX 3.4。顯示的是明度 62、暖 0.31、對比 6.2:1，這些是物理量不是評價，不會被誤讀成預測力。
