## 3. heavenraven 案例拆解與 Lava 的差距

**成功要素按貢獻排序（我的判讀）**：

1. **主角自帶流量。** Tom Holland 是全球級 IP。27.7k 讚裡有多少是結構功勞、多少是人臉功勞，無法分離。移植前要先承認這一條。
2. **證據密度。** 每條都是可查證的具體事件加年份。這是內容功勞，可移植。
3. **兩次反轉。** 先推到「太扯了真有顯化」，再自我否定「全歸功顯化太簡單」。第一層留人，第二層產生分享與收藏。`tpl-manifest-proof-chain` 的 `why_it_works` 抓得很準。
4. **第三方證言鏈。** 說服力來自旁人不是本人。可移植但素材最難拿。
5. **視覺：圖是主角，字是配角。** 每張一句話。
6. **Caption 逐行斷句。**

**Lava 做不出來，差距按嚴重度排**：

**差距一：文字量級差一個數量級，而且正在惡化。**

我算了 `posts.json` 全部 177 張非 CTA slide [驗證]：

| 指標 | 數值 |
|---|---|
| 超過 140 字的張 | 102 / 177 = **58%** |
| 中位數 | 152 字 |
| P90 | 245 字 |
| 最長 | 349 字 |

川口春奈那篇 slide 3-6 是 247／333／259／287 字，連續四張知識牆。而 7 月的篇均是 86-146 字，8 月的篇均是 148-210 字。**沒有任何機制在擋，字數在自己漂移。**

S2 提的 `over_length`（>140 block）方向完全正確，但沒有人算過它會擋掉現有 58% 的張。上線第一天等於全線 block。

**差距二：版式只有一種。**

`render_post_v5.py` 只有 `render_cover` 與 `render_content` 兩個渲染函式 [驗證，讀 code 第 349 與 417 行]。八張內容頁共用同一個版式：logo 左上、黃字標題、橘槓、正文底部錨定、footer。

S3 §4.1 的節奏合約列了 hero／滿版／頂錨漸層／上下分割／collage 五種版型。S3 §4.3 自己標了這個依賴，但措辭是「只能拿到一半效果」。**實際上是完全無效**：RH1-RH3 只約束選哪張圖，讀者看到的仍然是九個一模一樣的框。

**差距三：證據型態不對等。** heavenraven 的證據是可視覺化的具體事件，Lava 的證據是研究引用（Gottman、Arthur Aron、Helen Fisher）。研究沒有畫面，只能配 mood 圖，所以 Lava 的圖永遠是裝飾。這正是四張知識牆的成因：沒有畫面，只好用字補。

**差距四：caption。** Lava 現況是三段密文加 15 個 hashtag。這一項改動成本最低，今天就能改成逐行斷句。

## 4. 「人物＆書籍＆概念」怎麼落地

**先說判斷：這可能是七份文件裡最有機會做出 10x 的單一改動。** 它把 Lava 從「教你怎麼約會」的說教位置，換到「講一個人怎麼活」的敘事位置。分享說教會顯得在教訓朋友，分享人物故事不會。這個差異直接打在 sends/reach 上。

**現有九張結構不適合，具體哪裡不適合**：

現行 roles（Hook／共感場景／知識解釋×4／品牌立場／應用怎麼做／CTA）是論說文骨架。人物題要的是時間軸骨架。「知識解釋×4」對應到人物題會變成「介紹這個人的四個面向」，那是維基百科不是敘事。`tpl-manifest-proof-chain` 的骨架是證據鏈 3-5 張、轉折 1 張、證言鏈 3-4 張、收尾，總長 9-13 張，角色分配跟現行九張完全不同。

**第一個卡點：三個新模板現在跑不了。** `templates.json` 的三個 mind 模板 status 全是 candidate，而且模板只有 `skeleton` 的文字敘述，**沒有 `slides` 結構欄位** [驗證]。也就是說 WF01 撰稿時無法照模板產出，模板現在是給人看的參考，不是給機器跑的規格。

**落地三件事，按順序**：

1. **先做 `tpl-persona-column` 的欄目制。** 固定 2-3 個欄目名（例如「Lava 觀察」談現象、「Lava 人物」談人、「Lava 研究」談研究），封面左下角固定標籤。它同時解決帳號辨識度與 S3 反覆抱怨的節奏問題，實作只需在 `render_cover` 加一段標籤繪製，不到 30 行。
2. **把模板從描述變成規格。** 每個模板加 `slides` 陣列，逐張標 role、字數上限、圖片 role、版型。沒這一步，模板不能驅動撰稿與排版。
3. **人物題的素材路徑要跟現有分開，而且要在選題時就判定。** 人物題不能配 mood 圖，只能用該人物的真實影像。這直接撞 S3 §1.6 的法遵紅線。可行的只有兩條：Wikimedia Commons 的 CC/PD 人物照（覆蓋率低，多半紅毯照）、YouTube 訪談影格（`forage_shots.py` 已支援，實測 yt_frame 39 張）。**建議在雷達卡加一個機器可判欄位：該人物是否有 ≥5 張可用影像。選題時就擋掉配不到圖的人選**，不要寫完稿才發現。

**還有一件不好聽的**：人物題的天花板由人選決定。heavenraven 用 Tom Holland，Lava 用 Gottman 或 Arthur Aron，自帶流量差三個數量級。要往上打，人選必須是台灣 25-34 歲認得的人，不是心理學家。這會逼出定位問題：Lava 要不要談流行文化人物。**這是 Jesse 要拍板的策略決定，不是工程問題。**

## 5. 搜圖＋策展能不能到 heavenraven 的視覺水準

不能，而且差距不在策展規則。

**一、素材型態不同。** heavenraven 的視覺一致性來自「同一個主角的多張影像」。Lava 的 mood 圖是不同攝影師、不同場景、不同色調的圖庫照拼起來。S3 的 R5 明暗交替、R6 構圖配額都是在補這個先天缺陷，補得再好也只是「不刺眼」，不會變成「一致」。

**二、法遵位置不同。** heavenraven 用劇照是無授權使用，他們承擔風險。S3 §1.6 正確地把這條劃成紅線。Lava 選擇合規，就等於選擇了較低的攝影天花板。這是已經做出的取捨，工程補不回來。

**三、版式只有一種。** 就算每張圖都完美，九張同一個框仍然平。

**我的建議：Lava 應該放棄追攝影感，改走設計感。** S4 §3 的 C/D/E（App UI 渲染、數據卡、品牌卡）方向完全正確，S4 自己也把它排第一批。這是七份文件裡我最同意的一個排序：渲染卡不需授權、沒有 AI 味、字型正確、成本 $0，而且能立刻打破九張同版式。真實攝影感的正解是 S4 §9 自己講的那句：辦一場真實聚會拍 200 張照片，期望值高於把生圖環節工程化。

## 6. 這套設計最可能在哪裡失敗

**失敗一（機率最高）：測量地基已經停擺，沒人發現。**

`data/insights.json` 的 `updated_at` 是 **2026-07-27**，今天 8-13，**17 天沒有新快照** [驗證]。8 月發的 5 篇一筆成效資料都沒有。

S1、S2、S6、S7 全部依賴「累積 N 篇乾淨資料後校準」。S7 §9 甚至把測量地基排在第 1 位。但實際狀況是資料採集在停擺。如果 WF11 繼續不跑，90 天後手上仍然是 5 筆快照，所有實驗設計、rubric 校準、Brier 分離度檢查全部作廢。

**這件事比任何 UI 改版都優先。** 建議把「insights 最後更新時間」做成頂欄的一顆燈，跟 Drive 掛載燈同一排。系統安靜地退化是這個專案最典型的失效模式，S1 §6 自己就是這樣描述來源健康的，現在它已經發生在成效資料上。

**失敗二：七份文件同時開工，一個旋鈕都測不出來。**

S2 §5 自己寫了「一次只動一個旋鈕」，然後七份文件各排了 6 到 9 週施工表，加起來是全部同時動：換選題來源、換寫手、換 hook 標準、換策展、加生成、換發文時段、換指標定義。任何成效變化都無法歸因。

更實際的風險是時間。七份文件的估時加總約 6 到 8 週工程量，而系統同時在生產運轉。

**建議 90 天只做三件事**，其餘進口袋：
1. 測量地基（S7 §9 的第 1 到 5 項）
2. 渲染卡 + 第二種內容版式（S4 §3 的 D/E，加 `render_post_v5.py` 一個 content layout）
3. 欄目制人物題（`tpl-persona-column` + `tpl-manifest-proof-chain` 規格化）

共同點：**不依賴統計顯著性就能見效。**

**失敗三：新規則把現有產出全面 block，Jesse 反而更累。**

S2 的 `over_length` 會擋掉現有 58% 的 slide，H1/H3 是 block 級；S3 的 R1-R8 有五條硬淘汰；S6 的 H1-H8 全部硬擋。這些規則沒有一條在現有 25 篇上跑過回歸。

UIUX §4.4 的影子模式（先跑兩週只記錄不阻擋，推翻率 <10% 才升級）是對的解法，但它只寫在總體架構的一小節，S2/S3/S6 各自的施工表都是直接上 block。**這個矛盾沒有人整合。** 建議把「所有新 block 規則先跑影子模式」升成跨文件硬約束，寫進 config。

**三個較小但會咬人的**：

- **去重已經在失效。** `posts.json` 現在有一組**完全相同**的 topic 重複（寵物去世後 ×2，都在 awaiting_review）[驗證]。另有 4 篇同開場「欸…你有沒有發現」，其中 2 篇用 `⋯` 2 篇用 `…`，現行 hook_repeat 因字元不同而漏掉 [驗證]。S1 設計了 L1/L2/L3 三層去重，但連 L1 的正規化都還沒統一全形省略號。先修這個比接 embedding 便宜一千倍。
- **積壓 14 篇 awaiting_review**，UIUX 的 WIP 上限設 6，上線第一天就紅燈。而這 14 篇用舊標準寫，新規則一上會全變 block。要先決定清掉還是豁免。
- **`posts.json` 473KB / 25 篇**，UIUX §7.1 推算 53 篇撞 GitHub API 1MB 上限。排進 B0 是對的，不要往後挪。
