### 1.2 分層設計

**L0 北極星｜Jesse 分鐘數／篇**

這個指標 **IG API 拿不到**，必須在操控室埋 instrumentation。這是整個環節裡最需要新做的東西：

```
docs/app.js 新增事件，寫入 data/effort_log.json
  review_open   {post_id, ts}
  slide_switch  {post_id, slide_idx, ts}
  copy_edit     {post_id, slide_idx, ts, char_delta}
  approve       {post_id, ts}
  schedule_set  {post_id, ts}
```
分鐘數 = Σ(相鄰事件間隔，上限 5 分鐘/間隔，超過視為離開)。拆解：選底圖分鐘 / 改文案分鐘 / 排程分鐘。這三個拆解決定下一輪要優化哪個環節。

**L1 成長｜非追蹤者觸及中位數**

媒體層 **沒有** follower/non-follower 拆分。可行的代理：帳號層 `reach` 的 `follow_type` breakdown 是日粒度，而 Lava 一天發一篇，所以可用「發文當日帳號層非追蹤者 reach」近似該篇。

```
GET /{ig-user-id}/insights
  ?metric=reach&period=day&metric_type=total_value
  &breakdown=follow_type&since=<D>&until=<D+1>
```
**[待查]** `follow_type` 與 `media_product_type` 能否同時傳兩個 breakdown（要把 Stories 的觸及排掉）。文件沒說。要實測。若不行，退而用「當日只發 FEED、不發 Story」的日子當乾淨樣本。

為什麼要用非追蹤者觸及而不是總觸及：追蹤者觸及有天花板（200 人），變異幾乎全來自推薦流。用非追蹤者觸及當主指標，訊噪比明顯較高 **[推理]**。

**L2 內容品質**（分母是 reach，回答「看到的人買不買單」）

| 指標 | 算式 | 為何重要 |
|---|---|---|
| 收藏率 | `saved / reach` | 知識型輪播的核心價值訊號 |
| 分享率 | `shares / reach` | IG 演算法權重最高的訊號 |

## 2. 歸因分析

### 2.1 現在的問題不是樣本少，是特徵沒記錄

`posts.json` 每篇只有 `topic`、`topic_type`、`version`。就算未來累積 50 篇，回頭也標不出「這篇的 hook 是什麼型式、封面用了什麼策略」。**特徵標註必須在發文當下寫入，事後補標不可信。**

要新增的欄位（由 WF01 撰稿階段與排版階段自動寫入，不靠人工）：

```json
{
  "features": {
    "hook_type": "反直覺斷言|數字清單|場景提問|權威引用|自嘲告白",
    "angle": "知識解釋|情緒共感|行為指南|品牌立場|時事嫁接",
    "evidence_type": "學術研究|媒體報導|素人觀察|無出處",
    "cover_type": "hero|collage",
    "visual_roles": ["person","mood","evidence","book"],
    "visual_source": "ddg|youtube_frame|screenshot|book_api|design_bg",
    "template_id": "T07",
    "writer_model": "opus-5|sonnet-4-6",
    "slide_count": 9,
    "cover_char_count": 24,
    "publish_slot": "wkday_2000|wkday_1200|wkend_1100",
    "curation_score": 7.5,
    "virality_score_pred": 8
  }
}
```

這是整個升級案的**第一優先**，其他都可以晚做，這個晚做一天就永久損失一天資料。

### 2.2 小樣本下該做什麼、不該做什麼

**不該做**：均值比較、t 檢定、任何「A 比 B 高 18%」的敘述。n=5 時 18% 的差異落在噪音裡（§3 有數字）。

**該做的三件事**：

**(a) 只抓 outlier，不做全面統計。** HANDOFF 已有這條規約（`>2× 中位數 → repurpose`），保留並雙向化：

- 上 outlier：reach > 2× 中位數 → 進 repurpose 佇列，且觸發「拆解報告」
- 下 outlier：reach < 0.5× 中位數 → 觸發「排除清單」，該題材／型式暫停 4 週

以現況中位數 216 計，門檻是 >432 與 <108。目前 6 篇裡有 1 篇（408）接近上門檻。

**(b) 比率用 Bayesian 收縮，不用原始比值。** 現況 reach=134/saved=1（0.75%）與 reach=260/saved=2（0.77%）看似不同，實際差異全是噪音。用 Beta-Binomial 收縮到全站先驗：

```
posterior_rate = (saved + α) / (reach + α + β)
α, β 由全站歷史 saved/reach 用 method-of-moments 估
```
零 AI，`scripts/weekly_report.py` 十行 Python。輸出時一律附 95% 可信區間，UI 直接顯示區間而不是點估計。

**(c) 配對式質性拆解，每 10 篇一次。** 不是讓 Claude 「看數據找原因」（會生成看起來合理的胡說），而是：

1. 本機腳本挑出 reach 最高 2 篇與最低 2 篇
2. 機械列出這 4 篇在 `features` 上所有欄位的差異矩陣（零 AI）
3. Claude Opus 5 只做一件事：**在差異矩陣裡指出哪些是「唯一差異」（其他三篇都相同、只有這篇不同）**，並把它寫成一條可證偽的假設
4. 輸出格式強制為：`假設 / 支持樣本數 / 反例數 / 建議驗證方式 / 信心(低|中|高)`
5. 信心「高」需要 n≥8 且無反例。不滿足一律標「低」

這樣 Claude 不被允許發明原因，只能從已標註特徵裡挑。

### 2.3 樣本門檻表（明確寫出什麼樣本量能回答什麼問題）

| 累積篇數 | 能回答 | 不能回答 |
|---|---|---|
| < 10 | 只有 outlier 識別 | 任何比較 |
| 10-20 | 各特徵值的 n 分佈是否足夠、CV 重新估計 | 特徵間比較 |
| 20-40 | 大效果（>50%）的單維度比較、配對比較 | 中小效果、交互作用 |
| 40-80 | 中效果（30%）的單維度比較 | 交互作用 |
| > 80 | 多維度迴歸 | |

UI 必須把每個特徵值的 n 顯示出來，n<8 一律灰掉。

## 3. 實驗設計

### 3.1 先算清楚這個帳號的統計極限

現有 5 篇最新快照 reach：260, 200, 408, 146, 216。
均值 246，標準差 99.3，**變異係數 CV = 0.40**。

雙組比較所需樣本（α=0.05, power=0.80）：

```
n/組 ≈ 2 × (1.96 + 0.84)² × CV² / δ²  =  2.51 / δ²
```

| 要偵測的相對效果 δ | n/組 | 總篇數 | 每日一篇的天數 |
|---|---|---|---|
| +20% | 63 | 126 | 126 天 |
| +30% | 28 | 56 | 56 天 |
| +50% | 10 | 20 | 20 天 |
| +70% | 6 | 12 | 12 天 |

**這是本設計最重要的一個數字，也是最需要被說出來的一句話：在 90 天窗口內，這個帳號只能可靠偵測 +50% 以上的效果。任何「這個 hook 讓觸及提升 20%」的結論在這個樣本量下都是噪音。** 團隊要先接受這個約束再談實驗。

**[待查／自我批評]** CV=0.40 是用 5 個觀測值算的，5 樣本的 sd 估計 95% CI 大約是真值的 0.6 到 1.7 倍。若真實 CV 是 0.65，上表所有數字要乘 2.6，90 天內做不完任何一個實驗。**因此第一件事是先累積 20 篇乾淨資料重估 CV，在那之前不要對 Jesse 承諾任何實驗時程。**

### 3.2 三個提高統計效率的手段

| 手段 | 做法 | 預估效益 |
|---|---|---|
| log 轉換 | 對 reach 取 log 再比較 | 長尾（408 那種）不再主導變異 |
| 配對設計 | 同 `angle` + 同 `topic_type` 的兩篇配成一對，只在對內比 | 消掉主題變異，n 需求約砍半 **[推理]** |
| 換主指標 | 用非追蹤者觸及取代總觸及 | 追蹤者觸及是常數項，移除後 CV 下降 **[推理]** |

三個疊加後，+30% 效果的需求可能從 56 篇降到 25-30 篇（約 4 週）。這需要實際資料驗證，不能先當定論。

### 3.3 實驗排程（90 天，只做三個）

**實驗 1｜發文時段（Day 1-28，n=28）**

- 為什麼先做：時段是乘數效果，對所有貼文型式都適用，是槓桿最高的單一變數
- 設計：兩個時段 A / B 逐日交替（switchback）。A = 平日 20:00-21:00，B = 平日 12:00-13:00
- 為什麼 switchback 而非隨機：逐日交替自動平衡星期效應與帳號成長趨勢
- 主指標：log(非追蹤者觸及)
- 樣本：14 / 組
- 判準：|效果| > 50% 且 95% CI 不跨 0 → 採納。否則宣告「無法區分」，改用同一時段（減少變數）
- 註：受眾活躍時段可先用 IG 內建 Insights 的 Active Times（App 內看得到，API 拿不到）當先驗，縮小候選

**實驗 2｜封面型式 hero vs collage（Day 29-60，n=32）**

- 為什麼：`render_post_v5.py` 已有雙版機制但「選擇機制不明確」，這個實驗直接把它變成資料驅動
- 設計：配對式。同一 `angle` 的相鄰兩篇分派不同 cover_type
- 主指標：log(reach)。次指標：D1/D7 達速比（封面決定的是首屏點擊率，會反映在爬升曲線前段）
- 判準同上

**實驗 3｜hook 型式（Day 61-90，n=30）**

- 只比兩個型式，不做多臂。從 §2.2(c) 累積的假設裡挑呼聲最高的一個 vs 現況主流
- 主指標：log(reach)
- 註：這是最想做但最不該先做的實驗，因為 hook 效果量通常小於 50%，樣本吃不下

### 3.4 一條不做 A/B 的替代路線

低流量帳號的正確策略，坦白說，是**用對標帳號已驗證的模式**，而不是自己從噪音裡學。實驗只能驗證少數幾個高效果變數，其餘決策應該來自 §4 的競品拆解與 `templates.json` 的 swipe 庫。實驗計畫的價值在於「防止把噪音當洞察」，不在於「產生大量洞察」。

## 4. 競品對照

### 4.1 官方免費路線：Business Discovery

**[驗證]** `business_discovery` edge 在 2026 仍可用。單次呼叫可取得任一**公開專業帳號**的資料：

```bash
curl -G "https://graph.facebook.com/v23.0/{your-ig-user-id}" \
  -d 'fields=business_discovery.username(thewknd.club){
        followers_count,follows_count,media_count,biography,
        media.limit(25){id,caption,like_count,comments_count,
                        media_type,permalink,timestamp}}' \
  -d "access_token=$LAVA_IG_TOKEN"
```

可取得欄位 **[驗證]**：`biography, id, ig_id, name, username, website, profile_picture_url, followers_count, follows_count, media_count`；媒體邊：`id, caption, comments_count, like_count, media_type, media_url, permalink, timestamp, children`。

**拿不到**：對方的 reach / saved / shares / views / 任何 insights。只有 likes 與 comments 的公開計數。

**限制**：
- 目標必須是 Professional（Business / Creator）帳號。**[待查]** @thewknd.club（46K）與 breeze.social（64.6K）是否為專業帳號，需實測一次確認
- 需要現有 token 的權限（`instagram_basic` + `pages_read_engagement`），Lava 的 token 於 2026-07-22 重產時已帶完整權限，**[推理]** 大機率可直接用
- 速率限制：Business Discovery 官方公式為 `200 × app 使用者數 / 小時` **[驗證，來自第三方彙整]**。每日 3 個帳號各 1 次，遠低於限額
- 來源：https://gist.github.com/jameschapman2c/65eff9f54a2d350b17a6ce5127b9fe42

### 4.2 從公開數字能推出什麼

| 衍生指標 | 算法 | 用途 |
|---|---|---|
| **粉絲日增** | `followers_count` 差分 | 最有價值的單一訊號。哪一天暴增 → 回看那天前後發了什麼 |
| 互動率代理 | `(likes + comments) / followers_count` | 跨帳號規模不同，只能同帳號縱比 |
| **內部相對表現** | 單篇 likes / 該帳號近 25 篇 likes 中位數 | **正確用法**。找出對方自己的爆文 |
| 發文節奏 | timestamp 序列 | 頻率、時段、間隔 |
| 型式配比 | `media_type` 分佈（IMAGE / CAROUSEL_ALBUM / VIDEO） | 對方把資源押在哪 |
| 題材分佈 | caption 送 Claude 分類 | 對方的內容組合 |

**關鍵判讀原則**：46K 帳號的 likes/follower 不能直接跟 200 追蹤者的 Lava 比。唯一可移植的訊號是「**對方的哪些貼文是他自己的 outlier**」，那才代表題材或型式本身有推薦流吸引力，而非粉絲基數效應。

**外部校準用途**：把對標帳號的爆文與 Lava 的爆文放在同一張特徵矩陣上比對，能區分兩種失敗：題目不對（對方同題材也不爆）vs 分發不足（對方同題材爆而 Lava 沒有）。這是 5 篇樣本下唯一能做的因果切分。

## 5. 回饋迴圈

**載體**：一份機器可讀的 `data/learnings.json`，由週任務產生，被各環節的 prompt 直接讀取。**不是**讓 Claude 每次自己去看數據（會每次得到不同結論）。

```json
{
  "generated_at": "2026-08-12",
  "sample_size": 12,
  "confidence_floor": "low",
  "topic_clusters": {
    "validated":  [{"cluster": "弱連結/社交圈", "n": 3, "reach_median": 285, "vs_overall": "+32%", "confidence": "low"}],
    "falsified":  [{"cluster": "已讀不回", "n": 2, "reach_median": 173, "vs_overall": "-20%", "confidence": "low"}]
  },
  "hook_types":   { "反直覺斷言": {"n": 4, "reach_median": 260, "ci": [180, 350]} },
  "templates":    { "T07": {"n": 3, "reach_median": 240} },
  "slots":        { "wkday_2000": {"n": 6, "reach_median": 255} },
  "cover_types":  { "hero": {"n": 4, "reach_median": 231}, "collage": {"n": 2, "reach_median": 254} },
  "score_calibration": {
    "virality_score_vs_reach": {"spearman": 0.11, "n": 12, "verdict": "no_signal"},
    "curation_score_vs_reach": {"spearman": 0.34, "n": 12, "verdict": "weak"}
  }
}
```

### 各環節的具體接法

| 環節 | 機制 | 判準 |
|---|---|---|
| **1 選題** | `learnings.json.topic_clusters` 注入 WF05 prompt，分「已驗證叢集（優先）／已證偽叢集（禁用 4 週）」兩份清單 | 進「已證偽」需 n≥3 且中位數 <0.7× 全站 |
| **1 選題（病毒分校準）** | 每 10 篇算一次 `virality_score` 與實際 reach 的 Spearman ρ。**若 \|ρ\| < 0.3 且 n≥20，停止用該分數當放行閾值，降級為純排序參考** | 這是可機器驗證的判準，不是「用數據優化」的空話 |
| **2 撰稿** | `hook_types` 表（各型式的 n / reach 中位數 / CI）注入 WF01 prompt。禁句清單自動加入 n≥5 且中位數 <0.7× 的 hook 型式 | 現況「欸，你有沒有發現」屬空洞 hook，機械檢查已擋，不靠成效 |
| **2 撰稿（A/B 裁決）** | Opus 5 vs Sonnet 4.6 雙指標裁決：① 操控室被選中率 ② 發佈後 log(reach)。累積 20 篇後看被選中率是否 >65%，reach 是否 CI 不重疊 | 被選中率是快指標（每篇即得），reach 是慢指標。快指標先動，慢指標確認 |
| **3 圖片搜尋** | `curation_score`（WF14 vision 評分）與實際 reach 的 ρ 校準，同病毒分規則。高表現貼文的 `visual_roles` 組合回饋成 role 配額建議 | ρ<0.3 → WF14 分數只用來擋爛圖（絕對門檻），不用來排序 |
| **4 圖片生成** | 目前近乎停用，無成效可回饋。等生成上線後才接，接法同環節 3（`visual_source` 進 features，比對各來源的 reach 分佈） | 不預先設計，避免空轉 |
| **5 排版** | `templates` 與 `cover_types` 表直接驅動選擇：封面雙版改為「按 `angle` 查 learnings.json 的歷史勝率，n<5 時隨機（同時是實驗 2 的資料來源）」 | 這同時解決「封面選擇機制不明確」與「實驗 2 資料收集」 |
| **6 排程** | `slots` 表推薦 `publish_at` 預設值，操控室日曆顯示各時段歷史中位數。實驗期間由 switchback 排程器強制交替 | |
| **7 成效本身** | 快照節點固定為 **D1 / D3 / D7 / D14 / D30**（見下） | |

### 5.7 快照節點改造（優先度僅次於特徵標註）

現況每日快照導致每篇資料在不同天數，跨篇無法比。改為：

```
WF11 每日 10:00 掃 posts.json，對每篇計算 published_at 距今天數
若落在 {1, 3, 7, 14, 30} 之一 → 拉 insights → 寫入 snapshots[day="D7"]
否則跳過
```
所有跨篇比較一律用 **D7**（爬升已趨緩、長尾尚未影響）。D1 用來算達速比，D30 用來看長尾。

|---|---|---|---|---|

| 拉競品快照 | n8n WF16（新） | 每日 09:30 | 無 | $0 |
| 拉 PostHog UTM 匯總 | 本機 cron | 每日 | 無 | $0 |
| 描述統計＋Bayesian 收縮＋ρ 校準 → `learnings.json` | 本機 `weekly_report.py` | 每週一 | 無 | $0 |
| 配對式質性拆解（產假設） | Claude | 每 10 篇 | **Opus 5** | ~$0.25/次 |
| 競品爆文拆解（caption 分類 + outlier 解讀） | Claude | 每月 | **Haiku 4.5** 分類 + **Opus 5** 解讀 | ~$0.35/月 |
| Jesse 分鐘數統計 | 本機 | 每週 | 無 | $0 |

**成本推算 [驗證，價格取自 Anthropic 官方模型表]**
- Opus 5 `claude-opus-5`：$5 / M input、$25 / M output
- Haiku 4.5 `claude-haiku-4-5`：$1 / M input、$5 / M output

質性拆解單次：input ≈ 30K（30 篇特徵矩陣 + 統計表 + 4 篇全文）、output ≈ 4K
→ 30K × $5/M + 4K × $25/M = $0.15 + $0.10 = **$0.25**

每月頻率：質性拆解約 3 次（每 10 篇）+ 競品 1 次 = **約 $1.1 / 月**

相對現況月成本 $15 級距，成效追蹤的 AI 成本可忽略。**設計原則：AI 只在低頻判斷節點出現，每日高頻工作全部零 AI。**

**人審關卡只設一個**：`learnings.json` 進入 prompt 前，Jesse 在操控室看一次「本週新增／變更的規則」diff（通常 0-3 條），核准才寫入。這符合「每個 AI 產出都要有人審，但 Jesse 一人不能疲乏」的約束。

## 8. 我這套方案裡最弱的三環

**最弱：整套實驗計畫的統計基礎建立在 5 個觀測值算出的 CV=0.40。**
5 樣本估 sd 的 95% CI 大約是真值的 0.6 至 1.7 倍。若真實 CV 是 0.65，§3.1 表格所有樣本量要乘 2.6，90 天內做不完任何一個實驗，整個 §3.3 排程作廢。
**處置：先累積 20 篇乾淨資料（固定 D7 快照 + 特徵標註）重估 CV，在那之前不對 Jesse 承諾任何實驗時程。** 這意味著 §3 的內容前 20 天只是「資料收集規格」，不是「實驗」。

**次弱：`profile_activity` + `action_type` 是我整個轉換歸因層的地基，但我只從 Meta 文件的表格查到它存在，沒有實際回傳驗證，且有第三方文件宣稱 API 拿不到。**
若驗不到，「哪一篇貼文帶來 bio 點擊」只能靠 hub 落地頁，多一次點擊會顯著壓低轉換，而以現況個檔瀏覽 0-5 的量級，hub 路徑的樣本量幾乎為零，轉換歸因整層等於廢掉。
**處置：這是第一個該跑的 curl，一次就能定案，不要等到實作階段才發現。**

**第三弱：用帳號層日資料代理單篇非追蹤者觸及，前提是當日只發一篇 FEED 且 Stories 不干擾。** 但 Stories 觸及也計入帳號層 `reach`，要靠 `media_product_type` + `follow_type` 雙 breakdown 拆開，而文件沒說兩個 breakdown 能同時傳。若不行，L1 成長指標退回總觸及，訊噪比下降，§3.2 的第三項效率提升失效，樣本量需求回升。

**另外三個較小但要說的**：
- `views` 對 CAROUSEL_ALBUM 標記「In development」，可能回 400。若不可用，「輪播後段品質」完全沒有任何代理指標
- 兩個對標帳號是否為專業帳號未驗證，若不是，Business Discovery 整條路線作廢，競品對照退回 Social Blade 的粉絲曲線（無單篇資料）
- Jesse 分鐘數的 instrumentation 需要改 `docs/app.js`（869 行 vanilla JS，正在生產運轉）。北極星指標的採集本身是有風險的改動，建議先做成純新增的事件記錄（不改任何既有邏輯），失敗只損失資料不影響審核流程
