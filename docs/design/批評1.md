## 0. 一句話結論

這八份文件的分析品質很高，但**它們是八個人各自寫的**，彼此沒有對過帳。三份文件各自定義了一支同名的 `check_rhythm.py`，規則代碼互撞；同一個「候選圖分數 < 5」有三種互斥處置；張數模型有 9 張固定、5 到 10 張變體、9 張節奏合約三套並存。這些衝突在文件階段看不見，會在實作時變成隨機行為。

更根本的問題：**整套設計的規模假設錯了一個數量級**，而且錯在最痛的地方。任務配置抓到了 30 篇 vs 12 篇，但沒抓完：選圖台是為「一篇 74 張候選」設計的，實際送到操控室的是**每張 slide 中位數 4 張、最大 12 張** [驗證]。

而全案唯一現在就在燒的東西，八份文件裡只有 S6 提到，還排在第六順位：**n8n 執行額度現在就是超的狀態，3,000 > 2,500，0723 全線停擺的根因之一就是這個** [驗證，HANDOFF:328/334]。

## 1. 做不出來，或架構上不成立的

### 1.1 三支同名的 check_rhythm.py，規則代碼互撞（必須先合併，不然先寫的會被蓋掉）

| 文件 | 檔名 | 規則 | 資料來源 |
|---|---|---|---|
| S3 §4.2 | `scripts/check_rhythm.py` | RH1-RH3 | luma / composition / OpenCV Haar 人臉 |
| S5 §2.2 | `scripts/check_rhythm.py` | **R1-R8** | L / warm / text_ratio / tpl / dhash |
| S6 §2.3 | `scripts/rhythm_check.py` | **R1-R6** | topic_type / template_id / hook_type |

同一個檔名兩份不同設計，R1 到 R6 在兩份文件裡是完全不同的規則。這不是「哪一個對」的問題，是文件之間沒有對過帳。

**判斷：S5 那一版是對的。** 它讀的是成品像素，在渲染當下算，零 AI，不依賴任何未實作的欄位。S3 那版依賴 `composition` 這個還不存在的 vision 產出欄位，且 OpenCV 是新依賴（見 3.1）。S6 那版根本不是視覺節奏，是內容組合檢查，該叫別的名字（`content_mix_check.py`），而且它依賴 `timeliness` 與 `template_id` 兩個 `posts.json` 現在沒有的欄位 [驗證，我列過 posts.json 的 key]。

### 1.2 S3 §5 的「合併 curate 呼叫 9 → 1、逾時就改 streaming」在現有架構做不出來

[驗證，`forage_shots.py:477-500`] curate 走的是 n8n webhook（`CURATOR_URL`），Python 端是 `urlopen(req, timeout=150)`，一個同步 HTTP POST，逐 slide 分批（code 裡的註解寫得很清楚：「整包 30+ 張會逾時；單批 ≤8 張穩定」）。

S3 的緩解方案是「改用 `client.messages.stream()` + `get_final_message()`」。那是 Anthropic Python SDK 的 API。**n8n 的 HTTP Request 節點不做 streaming，也不會把 SSE 拆回來。** 這個緩解方案在 n8n 架構下不存在。

要做合併呼叫，前置條件是**把 WF14 從 n8n 搬回本機直打 Anthropic API**。S1 已經對 `collect_signals.py` 做過同一件事並寫了理由（「n8n 的 workflow 每改一次都要重新發布且連線不穩」），這條路是通的，但 S3 沒有把它寫進依賴裡。

**而且合併呼叫的金錢報酬是假的**：S3 自己算現況 $0.087、升級後 $0.070，差 $0.017/篇。12 篇/月 = **每月省 $0.20**。真正的理由有兩個，都不是錢：一是相對排序需要看整篇（分數穩定性），二是 **n8n 執行數從 9 降到 1**（見 1.6）。文件把次要理由當主標題了。

### 1.3 P4「證據對帳，HEAD 200 + 頁面含關鍵字，完全確定，$0」不成立

這是整條人物線唯一的防捏造機制，而它不會運作。

Tom Holland 那種「2013 年說想演蜘蛛人、三年後成真」的一手來源，絕大多數是 YouTube 訪談影片、有 paywall 的雜誌報導、或 JS 渲染的頁面。HEAD 200 只證明 URL 活著，不證明那句話在裡面。實際會大量落在 `not_found`，而 `not_found` 的處置在文件裡沒寫，唯一的出路是 Jesse 人工判讀。

**這條標成「純程式、$0、完全確定」是把成本從錢挪到分鐘數，直接打北極星。** 而且失效模式很糟：一條編造的名人證言掛在 Lava 官方 IG 上，是品牌傷害不是資料品質問題。

**替代做法**：把對帳從「驗證言論」降級成「限制來源型別」。P2 的 `web_search` 只收 Wikipedia、Wikiquote、以及帶結構化引文的維基資料；抽不到結構化出處的 claim 一律不進稿，而不是進人工佇列。產量會掉，但這條線本來就只有 4 篇/月。

### 1.7 Opus 5 + `thinking: disabled` 有兩個已知失效模式，兩份文件都沒提，而且對 Lava 是實害

[驗證，claude-api 官方遷移指南] Opus 5 在 `thinking: {type: "disabled"}` 下有兩個記載在案的失效模式：

1. **tool call 會被寫進可見文字而不是 `tool_use` block。** 該回合正常結束、不報錯、呼叫從未執行。
2. **`<thinking>` 之類的內部 XML 會洩進可見輸出。**

第二點對 Lava 是直接的實害：T2.4 定向改寫的輸出直接進 `display_copy`，`render_post_v5.render_content` 會照印在圖上，而 S2 的 14 條機械檢查**沒有一條擋 XML 標籤**。

官方建議的解法反直覺，而且跟任務配置的陷阱表相反：

- **不要關 thinking，改成開 adaptive 然後把 effort 降到 low 或 medium。** 成本一樣降，兩個失效模式都消失。
- 如果一定要關：**刪掉 prompt 裡任何「不要思考」「不要推理」的指令**（那會讓標籤洩漏更嚴重），而且反制指令要寫成通用的「不要輸出內部或系統 XML 標籤」，**不要點名 thinking 標籤**（點名的效果實測較差）。

任務配置的陷阱表寫「T2.4 固定 `effort: high` + `thinking: disabled`」。這條要改成 `thinking: adaptive` + `effort: low`。順帶：`display_copy` 應該加一條 `no_xml_tags` 機械檢查，五行。

### 1.8 WF01 現行的 web_search 工具版本是舊的

[驗證，HANDOFF:246] WF01 研究步驟用 `web_search_20250305`。[驗證，claude-api] Opus 5 支援 `web_search_20260209`，帶動態過濾（模型先寫程式篩結果再進 context，token 效率與準確度都較好）。

## 2. 為想像中的規模設計的

### 2.1 選圖台解的問題比宣稱的小 4 到 6 倍（最嚴重的一項）

S3 §6 與 UIUX §2.2 的核心前提是「現況每篇 15 到 74 張候選逐張看是最大的時間黑洞」，UIUX §4.1 進一步算出「9 張 × 平均 17 張候選 = 最多 153 次視覺比較」。

我實際算了 `posts.json` [驗證]：

```
25 篇，202 個 slide
每 slide 候選數分布：0張×46, 1張×13, 2張×9, 3張×25, 4張×11,
                      5張×49, 6張×11, 7張×4, 8張×15, 9張×4, 10張×3, 12張×12
每 slide 中位數 = 4，最大 = 12
每篇加總中位數 = 26，最大 = 74（只有 3 篇達到 74）
```

**74 是整篇加總，不是單張。** 而且 `app.js:252` 已經預選 `default_cid`，`app.js:307` 是把該 slide 的 4 張並排顯示。所以實際動作是：往下捲，看 9 組各 4 張的縮圖，覺得預選不對就點一下。不是 153 次比較。

S3 §6 那整套（三欄版面、`Tab` 跳旗標、`1-9` 跳張、`F` 放大、`X` 排除、`A` 全部接受、`Cmd+Enter` 送審、節奏儀表即時重算）是為了把「捲 74 張」變成「按 3 次 Tab」。實際要解的是「捲 26 張已排序的縮圖」。

**這不代表選圖台沒價值**，但它的價值排序要降。真正的痛點在 UIUX 自己指出的另一件事：**主舞台顯示的應該是成品渲染圖，不是裸底圖**。那一條是對的，而且改動小得多。

### 2.2 S1 的選題引擎是給每天從 3,000 筆選題的系統設計的

S 分六項加權、agglomerative clustering（cosine > 0.82）、L1/L2/L3 三層去重、新鮮度三指標、epsilon 探索抽樣、7 項 rubric、Brier 分離度追蹤。

實際需求是**每週挑 3 個題**。而且 S1 自己承認最弱環是「90 天內拿不到統計顯著性」，在 12 篇/月下只會更差（見 2.3）。

**這一層真正有價值的只有一樣，而且不是評分模型：來源健康表。** S1 §6 自己寫得很清楚：「22 個來源必然會壞，壞掉不告訴 Jesse 的話，系統會安靜地退化回只有 3 個來源，跟現在一模一樣，而且沒人知道。」

而這個東西**已經寫好了** [驗證]：`collect_signals.py` 的 docstring 有 `--health` flag，`data/signals/latest.json` 已經帶 `source_count` / `ok_count` / `sources` 欄位。把它接到既有的 ClickUp 告警通道（`sync_console.py:1160 alert()` 已經實作）大概 40 行。

S 分模型大概 400 行，而且需要 OpenAI embedding key（repo 目前沒有）。**40 行的價值高於 400 行。**

### 2.3 S7 的三個實驗在 36 篇的預算裡排不下

S7 §3.1 用 CV=0.40 算出偵測 +50% 需 10 篇/組（20 篇總）。但 S7 §8 自己承認 CV 是 5 個觀測值算的，真值可能是 0.65，那樣本量要乘 2.6。

12 篇/月 × 3 個月 = **36 篇**。S7 §3.3 排了三個實驗：時段 28 篇 + 封面 32 篇 + hook 30 篇 = **90 篇**。

而且這 36 篇還要扣掉：發文時段還沒固定的（前 4 週）、`features` 欄位還沒開始寫的（B0 之前）、快照節點還沒改成 D1/D3/D7 的。實際可比樣本 **[推理] 大概 20 到 25 篇**。

**90 天只能跑一個實驗，而且只能是效果量最大的那個。** S7 §3.3 自己說時段是「乘數效果，槓桿最高的單一變數」，那就只跑時段。封面與 hook 的實驗排進行事曆是自欺。

### 2.4 posts.json 拆檔（UIUX B0，+2 天）解的是一個大概 10 行能解的問題

現況 462KB / 25 篇 [驗證]，約 53 篇撞 1MB。以 3 篇/週算約 21 週（不是 UIUX 說的 9 週，因為那是用每日 1 篇算的）。

[驗證，`app.js:42-52`] `apiGet()` 用 `Accept: application/vnd.github+json` 讀 base64 `content` 欄位。**但 `rawUrl()` 已經存在（`app.js:38`），`publicRaw: true` 已經設好。**

最小修法：**sha 繼續走 contents API，內容改從 `raw.githubusercontent.com` 拿。** 大約 10 行。

**[待查] 我沒有實測 >1MB 檔案的 contents API 回應形狀**（`content` 是否為空、`encoding` 是否為 `"none"`、`sha` 是否照給）。動工前應該建一個 >1MB 的測試檔驗一次，一分鐘的事。

拆檔則要動 `app.js`、`sync_console.py`（9 處 load/save）、`check_typography.py:86`、`weekly_report.py:44`、`iterate_harness.py:228`、`verify_pipeline.py:20`、n8n WF10/WF11。**8 個消費者的遷移，換 21 週後的問題。** 而且就算 raw 那條路走不通，還有「每 30 篇歸檔」這條退路，`archive_data()` 已經實作了（`sync_console.py:1005`，任務 #5 已完成）。

### 2.5 A/B 雙寫手在 12 篇/月是浪費，而且 S2 自己寫了更好的方案卻標成「次要」

S2 §5 實驗 A：配對符號檢定，n=30 需 21/30 才 p<0.05。每週 3 篇 = **10 週**。而且前置條件是「兩稿必須共用同一組底圖」，S2 §5 第 4 條自己說「這是目前架構沒處理、實作最容易漏掉的地方」，要改 `visual_refs` 的產出點。

S2 §5 又寫了：**次要指標用 `review_seconds` 與 edit ratio，連續型，配對 t 檢定偵測 d=0.8 只要 n≈15。**

n=15 是 **5 週**，而且這兩個指標**直接就是北極星**（Jesse 分鐘數）。觸及是慢指標、噪音大、可能永遠測不出；分鐘數是快指標、每篇即得、直接對應目標。

**這應該是主指標，不是次要指標。** 而且如果只看分鐘數，甚至不需要盲測雙稿：跑四週 Opus，跑四週 Sonnet，比 `review_seconds` 中位數。省掉共用底圖的架構改動。

## 3. 成本估算：金錢沒低估，維護成本嚴重低估

S6 §5.2 的 B 案（slot cron，`29 20 * * 2,4` 等四條，`Pick Due Slides` 條件改成 `publish_at` 落在 `now ± 10 分鐘`）：**半小時工程、月增 $0、執行數 2,880 → 約 22，加上對帳 cron 約 55。**

而且它有一個隱藏紅利，S6 也寫了：視窗化條件天然解掉過期重貼（`archived-posts.json` 現在有兩篇過期 `scheduled`）。

### 3.3 $15 的組成沒查清楚，但方向可以先定

任務配置反推 API 現況約 $3.1/月，跟 $15 對不上，推論 $15 主要是 n8n Cloud 訂閱。

如果是這樣：**降 n8n 執行數不會馬上省錢**（訂閱是固定沉沒），**但會解掉停擺風險**；真正能省錢的是「執行數降到能退回免費層」。這件事要拿帳單確認一次，不要再推估。

### 3.4 Higgsfield 計費 [待查] 沒解決，整個環節 4 的成本估算建立在推估的影子價上

S4 §4.3 明說：官方 REST API 文件**沒有價目表，也沒說 API 用量是吃訂閱 credits 還是另計**。$0.17/篇的估算建立在「2 credits ≈ $0.07-0.09」這個影子價上，而影子價是用兩個互相矛盾的第三方來源（$129/月 3000 credits vs $99 年繳）推的。

S4 自己的結論也是先做渲染卡（零 AI），生成延後。**同意，而且應該更硬：Higgsfield 計費查清楚之前，環節 4 只做 D 與 E（數據卡、品牌卡），A 與 B 一行都不寫。**

### 3.5 一個小但確定的成本更正

prompt caching 的部分，任務配置的判斷全對，我獨立核對過 [驗證，claude-api]：TTL 5 分鐘（預設）/ 1 小時（2× 寫入）；Haiku 4.5 最小可快取前綴 **4,096 tokens**、Sonnet 5 **1,024**、Opus 5 **512**。S3 §5.2 的「Haiku 粗篩 + rubric 800 快取」確實會靜默不快取。

補一個任務配置沒提的：**Opus 5 的最小前綴從 Opus 4.8 的 1,024 降到 512**，所以以前寫不下的短前綴現在可以快取了。不改變 TTL 的結論（每 2 到 3 天一篇還是必然過期），但如果採「批次日一次產 3 篇」，快取會命中，而且門檻更低。

## 4. 七個面板真的都需要嗎

UIUX 把七環節收成六個面板，這個判斷是對的，理由（「環節是貼文的狀態，面板是 Jesse 的動作」）也是對的。

但依照上面的規模現實，**六個裡有三個現在不該做**：

| 面板 | 判斷 | 理由 |
|---|---|---|
| **審稿台** | **做** | 打瓶頸。14 篇 `awaiting_review` 積壓是實測 [驗證]。核心改動是「主舞台顯示成品渲染圖不是裸底圖」與「待決列例外處理」，這兩條與候選數多寡無關，成立 |
| **工作台看板** | **做，但簡化** | 「卡在哪」現在看不見是真問題（`render_note` 只躺在卡片裡）。但五欄 + WIP 上限 + 卡住側欄 + 拖拉是 2 到 3 天；先做**頂欄健康列 + 卡住清單**就有 80% 價值，半天 |
| **日曆** | **降級成一個 `<select>`** | 白名單 5 個 slot 用下拉選單就夠。S6 §7 的拖拉磁吸日曆（250 行 JS + 80 行 CSS grid + Cmd+Z undo stack + 409 重試 + 60 分凍結窗）是每週用一次的東西。**但 slot 白名單本身要做，因為 slot cron 依賴它** |
| **成效** | **延後** | UIUX 自己排第五批，理由「資料不夠時做了也沒東西看」。對，而且 12 篇/月下更久 |
| **雷達** | **不做面板，只做一欄** | UIUX 自己說「選題現在走 ClickUp 也能運作，UI 收益最低」。來源健康那一欄拉出來接 ClickUp 告警即可（見 2.2） |
| **規則** | **不做** | `config/*.md` 現在用 Claude Code 改，一人團隊沒有第二個人需要 GUI。推翻率統計有價值，但那是一張表不是一個面板 |

另外，UIUX §5 說「生成不是一個面板，是審稿台裡的一顆按鈕」，這條完全正確，應該推廣：**環節 4 的整個 UI（S4 §7 那個 prompt textarea + chip 選單 + 並排比較）在生成上線之前一行都不要寫。**

### 一個 UIUX 沒處理但會咬人的

UIUX §7.3 說「前端所有動作的正確模型是寫入意圖，由哨兵接手」，並提出加一個 60 秒快車道 watcher 處理 `data/jobs/urgent/*.json`。

**這會讓兩支 launchd agent 同時對同一個 git repo 做 pull / commit / push。** `auto_render.sh` 有防重疊鎖（`/tmp/lava-ig-autorender.lock`），但那是單支腳本的鎖。兩支不同的 agent 需要共用同一把鎖，而且快車道那支也要處理 stash pop 衝突（`auto_render.sh` 第 55 到 70 行那一整段血淚，2026-08-11 已經把 `<<<<<<<` 寫進 `posts.json` 一次）。

**建議：不要加第二支 agent。** 把哨兵的 `StartInterval` 從 600 降到 120，並在腳本開頭加一個「沒有 urgent job 且沒有新審核就 30 秒內退出」的快速路徑。同一支腳本、同一把鎖、同一套衝突處理。

## 6. 我這份審查裡最弱的一環

**最弱：2.4 的 posts.json raw 讀取方案我沒有實測。** GitHub contents API 對 >1MB 檔案回傳的形狀（`content` 是否為空字串、`encoding` 是否為 `"none"`、`sha` 是否照給）我是從文件記憶推的，標 [待查]。這直接影響「10 行 vs 拆檔 2 天」這個建議。動工前建一個 1.2MB 的測試檔打一次 API 就能定案，一分鐘的事，但我沒做。如果 sha 拿不到，這個建議就得換成「歸檔」那條退路。

**次弱：2.1 我說選圖台是為想像中的規模設計，依據是 `posts.json` 裡的候選數，但那是策展後的數字。** 如果 Jesse 實際會去點開「看被刷掉的 22 張」，或者他不信任 `default_cid` 所以每張都逐一比對，那體感黑洞可能真的存在。**這件事該用 `effort_log.json` 量兩週再決定，不該用我推。** 所以我把埋點排進 W1、把選圖台排進「等數據」，而不是直接砍掉。

**第三：我沒有讀 n8n 的實際 workflow JSON。** WF14 的 prompt、WF15 的判準、兩者的逾時設定，我全部是從 Python 端（`forage_shots.py:495` 的 `timeout=150`、`sync_console.py:1125` 的 `timeout=240`）反推的。S5 §3.1 說「n8n 端 prompt 我看不到」，我也看不到。所以我對「總檢判準不穩」的歸因（一次問五個維度、關係型判斷沒有中介表徵、輸出未被 schema 約束）跟 S5 一樣是推理，不是驗證。**如果 Jesse 願意花五分鐘把 WF14/WF15 的 prompt 貼出來，這一整塊的分析可以從推理升級成驗證。**

**第四：我對「品質」的判斷完全沒有依據。** 我審的是可行性、規模匹配、成本、衝突。但這套系統的目標是 90 天觸及中位數 10 倍成長，而 S4 §9 說了一句我認為是全部八份文件裡最重要的話：「Lava 真正缺的不是更好的生成圖，是自有素材。對標的 @thewknd.club 之所以 46K 追蹤，靠的是真實聚會的現場感。辦一場真實聚會拍 200 張照片，期望值高於把生圖環節工程化。」

我沒有能力判斷這句話對不對。但如果它是對的，那麼上面這四週的工程排序，最大的價值只是「讓每篇少花 Jesse 幾分鐘」，而不是「讓觸及成長 10 倍」。**這兩件事不是同一件事，八份文件裡只有 S4 §9 誠實地把它們分開講。**
