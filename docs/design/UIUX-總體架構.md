# Lava IG 操控室：整合設計文件 v1

給 PM 審。基於實讀 repo（`docs/app.js` 869 行、`data/posts.json` 25 篇、`scripts/auto_render.sh`、launchd plist）與七份環節提案。
標記規則：**[驗證]** 有出處或實測｜**[推理]** 從現有資料演繹｜**[待查]** 未驗證。

---

## 0. 設計主張（先定調，後面全部由此推導）

**七個環節不是七個面板。環節是「貼文的狀態」，面板是「Jesse 的動作」。**

現行四頁籤（審核／成效／提案／版本）的問題不是頁籤太少，是它把「系統做了什麼」當成分類軸。如果照環節切成七個頁籤，Jesse 每處理一篇貼文要在 5 個頁籤之間跳，因為選題、文案、選圖、生成、排版其實發生在**同一個物件**上。

所以整套設計的骨幹是兩條規則：

1. **一篇貼文從頭到尾只在一個工作區裡處理**（審稿台）。環節 2/3/4/5 全部收在裡面，以「軌道」而非「頁面」呈現。
2. **每個面板只回答一個問題**，回答不了就不該存在。

| 面板 | 它回答的唯一問題 | 涵蓋環節 |
|---|---|---|
| 工作台（看板） | 有東西可發嗎，卡在哪 | 1 放行、2-5 製程可視化 |
| 審稿台 | 這一篇能不能出 | 2、3、4、5 |
| 日曆 | 這週的組合對不對 | 6 |
| 成效 | 上一批學到什麼 | 7 |
| 雷達 | 下一批從哪來，來源健不健康 | 1 |
| 規則 | 系統為什麼這樣做，怎麼改它 | 全部的設定層 |

## 2. 各面板畫面組成

共用規格：8px 基準間距、`#0e0f11` 底（沿用現行 theme-color）、字級 12/13/15/20/28、圓角 8px、卡片 1px 邊框不用陰影。

### 2.1 工作台（看板） 最小可用寬度 1216px

```
┌ 頂欄：本週體檢 [知識●][時事○][品牌○]  違規 2  距下篇發佈 31h ─────┐
├─────────┬─────────┬─────────┬─────────┬─────────┬──────────────┤
│ 靈感放行 │ 製作中   │ 等你 6/6│ 待排     │ 已排     │  卡住 (側欄)  │
│  220px  │  220px  │  220px  │  220px  │  220px  │    240px     │
│         │         │  ▲紅色  │         │         │  虛線邊框     │
│ [卡]    │ [卡]    │ [卡]    │ [卡]    │ [卡]    │  [卡+原因]    │
│ [卡]    │ 進度條   │ [卡]    │         │ slot 名 │  [修復按鈕]   │
└─────────┴─────────┴─────────┴─────────┴─────────┴──────────────┘
```

- 五欄固定不可拖動順序。1216 = rail 56 + 5×220 + 側欄 240 + 間距。低於此寬度時整個欄區水平捲動，側欄摺成右上角一顆「卡住 3」按鈕。
- **卡片（220×112）資訊層級**，由上到下只有四層：封面縮圖 56px 方形靠左 ＋ 標題兩行截斷；第二行是閘門四點與型式色條；第三行灰字是「停在此欄多久」；hover 才出現動作按鈕列。
- 「等你」欄有 WIP 上限 6，超過時欄頭變紅並顯示 `14/6`。這是北極星（每篇消耗的 Jesse 分鐘數）的前導指標。
- 靈感卡點擊 → 右側抽屜 380px 顯示 heat_evidence、來源連結、去重比對結果、預測病毒分（顯示為「型式相近的前例中位觸及」而不是 1-10 分，理由見 3.4）。抽屜底部兩顆按鈕：放行、退回。
- 拖拉只允許「靈感放行 → 退回」與「待排 → 已排（開日曆選 slot）」。其他欄位的移動由系統決定，人不能手動改階段，避免狀態與資料不一致。

### 2.2 審稿台 最小可用寬度 1180px（關鍵路徑，見第 4 節）

```
┌ 待決列：本篇 3 項待決  [全部採用建議]  [核准 A]  [退回 R] ───────────┐
├──────┬──────────────────────────────────────┬─────────────────────┤
│ 佇列  │            成品預覽（主舞台）           │   本張的證據與編輯     │
│ 240  │                                       │       380           │
│      │  ┌─────────────────────────┐          │  ┌───────────────┐ │
│ 縮圖  │  │                         │          │  │ 文案編輯框      │ │
│ +閘門 │  │   選中那張的成品渲染圖     │          │  │ (逐條檢查標記)  │ │
│ 四點  │  │   最大高度 62vh          │          │  └───────────────┘ │
│      │  └─────────────────────────┘          │  候選圖 3 欄縮圖      │
│      │  ▔▔▔膠捲：9 張成品縮圖，待決的加紅框▔▔▔  │  查證與出處          │
└──────┴──────────────────────────────────────┴─────────────────────┘
```

- **主舞台顯示的是成品渲染圖，不是原始候選圖。** 現行流程讓人先選底圖再看成品，順序反了。人要判斷的是「這張成品能不能發」，底圖只是達成手段。
- 右欄是「本張」的所有東西，隨膠捲選擇同步。文案框內的違規詞用底線標出，滑過顯示規則代碼與建議改寫，一鍵採納。
- 候選圖 grid 預設只顯示前 6 張（策展分數最高者），「看全部 74 張」是一顆次要按鈕。**現況每篇 15 到 74 張候選逐張看是最大的時間黑洞** **[驗證，來自環節 3 現況]**。
- 低於 1180px：右欄改為覆蓋式抽屜。低於 900px：進入唯讀模式（已定案的手機降級），隱藏所有寫入按鈕，只留成品瀏覽。

### 2.3 日曆 最小可用寬度 1120px

- 預設週視圖，5 列（S1/S2/S3/S4/HOT）× 7 欄，一屏看完。月視圖只做唯讀熱度圖。
- 每格：封面縮圖 96px、型式色條（左緣 4px）、hook 型式文字徽章、時效標籤（熱點顯示剩餘小時）、閘門四點。
- 拖拉磁吸到白名單 slot。按住 Alt 才能放到任意時間，並警示「非白名單時段，時段實驗資料會被污染」。
- 距發佈 60 分內的卡片鎖定，需先按「取消排程」。
- 頂欄「本週體檢」與看板共用同一個元件，資料同源。

### 2.4 成效 最小可用寬度 960px

三段直式，不做多欄儀表板（資料量根本不夠撐滿一個 dashboard）：

1. **漏斗一列**：非追蹤者觸及 → 個檔瀏覽 → 追蹤／bio 點擊 → 落地頁。每級顯示絕對值與中位數，斷點自動標紅（現況「追蹤 5 篇全 0」會直接被標出）。
2. **篇級表格**：每列一篇，欄位是 D3 觸及、收藏率、分享率、hook 型式、封面型式、撰稿模型。可依欄排序，這就是歸因分析的全部介面，不做圖表。
3. **Jesse 分鐘數**：北極星專區，顯示每篇的選底圖／改文案／排程三段耗時與 30 日趨勢。

**硬規則：樣本數 < 10 的任何比較，介面上必須印「n=5，差異落在噪音內，不可據此決策」，而不是畫一根長條圖。**

### 2.5 雷達 最小可用寬度 900px

左 320px 是來源清單（22 個源），每列顯示最後成功抓取時間、本週產出的靈感卡數、狀態燈。右側是選中來源的近期訊號與去重命中紀錄。這個面板的價值是「哪個源沒在動」，不是給人讀新聞。

### 2.6 規則與設定 最小可用寬度 900px

左側分類：來源、文案規則、視覺規則、生成、版型、排程 slot、模型與成本、版本與回滾、憑證。右側是該分類的表單與**該規則的近 30 天觸發統計**（觸發幾次、Jesse 推翻幾次）。推翻率是調閾值的唯一依據，必須跟規則長在同一個畫面。

## 3. 跨面板一致性

### 3.1 狀態：拆成三個正交維度

現行混亂的根源是把「階段」「品質」「例外」擠在同一組 status 字串裡。實例：`docs/app.js:173` 那段已經出現 `approved + publish_at + !blocked = 重出中·排程保留` 這種四層三元運算，這是狀態模型漏了維度的症狀 **[驗證，讀 code]**。

**維度 A：階段（單選，回答「現在誰負責」）**

| 階段 | 顏色 | 由現有資料推導的規則 |
|---|---|---|
| 候選 | 灰框 | proposals.status = pending |
| 製作中 | 石墨 `#6B7280` | approved 且無成品且無 render_note |
| **等你** | **品牌橘 `#E84224`** | awaiting_review，或 approved + render_note |
| 待排 | 琥珀 `#B45309` | approved 且成品就緒 |
| 已排 | 藍 `#2563EB` | scheduled |
| 已發 | 綠 `#15803D` | published |

**品牌橘只用在「等你」一種情境，全站不再有第二個用途。** 看到橘色 = 我是瓶頸。這是整套視覺語言裡最值錢的一條約定。

**維度 B：閘門（四顆點，固定順序，回答「品質過了嗎」）**

`文案 · 事實 · 視覺 · 排版`，順序等同管線順序，位置固定在卡片第二行同一像素。灰=未跑、綠=過、琥珀=warn、紅=block。因為位置固定，「第三顆紅」可以被肌肉記憶。

**維度 C：警示（最多一個，回答「有沒有出事」）**

卡住（render_note 有值）／缺料（有 slide 0 候選）／過期（newsjack 超過 72h）／衝突（寫入 409 或哨兵未心跳）。表現為卡片右上角實心徽章加虛線邊框。

**硬規則：一張卡最多 1 階段 + 4 閘門點 + 0 或 1 警示，禁止任何其他標籤。** 「重出中，排程保留」不再是一個階段標籤，它是階段=製作中之下的一行灰色小字。

### 3.2 進度：三種型態，三種元件，不准混用

| 情境 | 元件 | 規格 |
|---|---|---|
| 已知步數 | 分段條 | 渲染 3/9 張，每格一張 |
| 未知時長但有輪詢 | 交辦式進度 | 「已交辦 14:32，哨兵下一輪 4:12 後」 |
| 全域背景 | 頂欄健康列 | 哨兵最後心跳、Drive 掛載、待跑數 |

**禁止使用無時間資訊的轉圈動畫。** 這一條直接解掉一個真實 bug 場景：`auto_render.sh` 在 Drive 未掛載時是**靜默 exit 0** **[驗證，讀 code 第 26 行附近]**，所以現況 Jesse 會看到卡片永遠停在「出成品中…」而系統從未告訴他為什麼。頂欄的 Drive 掛載燈就是為這件事存在的。

哨兵輪詢間隔 600 秒為已知常數 **[驗證，`tw.lava.ig-autorender.plist` StartInterval=600]**，所以倒數是可以精準顯示的，不需要猜。

### 3.3 錯誤：三級、三句、一顆按鈕

| 級別 | 樣式 | 行為 |
|---|---|---|
| 阻擋 | 紅底卡片 | 必附一顆修復主按鈕，不可核准 |
| 警告 | 琥珀左框，可折疊 | 附「知道了，仍要核准」 |
| 資訊 | 灰字單行 | 不佔垂直空間 |

文案一律三句：**發生什麼 → 影響什麼 → 你可以做什麼**。範例：「渲染沒有產出。原因是 Drive 未掛載，哨兵在 14:20 跳過這輪。掛載後按重試，或先審其他篇。」現行的 `寫入 posts.json 失敗 (409)` 這種只有錯誤碼的訊息全部改寫。

空狀態同理，每個空狀態都要帶下一步按鈕。

### 3.4 一條反過度自信的規則

任何 AI 產生的分數（病毒分、策展分、hook 分）**一律不以裸數字呈現**。改為「通過 4/6 項」加未通過項目清單，或「型式相近前例的觸及中位數」。理由：病毒分從未用實際成效校準過 **[驗證，環節 1 現況]**，顯示成 8.5 分會讓人把它讀成預測力。查證結果同理，標「已驗到出處層」而不是綠勾。

## 4. 關鍵路徑：把審稿從「逐張決定」改成「例外決定」

### 4.1 現況的時間都花在哪

現行流程：佇列 → 點入 → 逐張選底圖（15 到 74 張候選）→ 文案編輯 → 核准 → 設排程。
決策點數量：9 張 × 平均 17 張候選 = **最多 153 次視覺比較**，加 9 次文案閱讀 **[推理，候選數來自 `quality_metrics.jsonl` 中位 17]**。

單篇實際耗時目前**沒有量測** **[待查]**。所以本節不承諾「從 X 分鐘壓到 Y 分鐘」，只承諾把決策點數量降一個數量級，並先把量測埋進去（見第 6 節 B0）。

### 4.2 新流程：四步

```
1. 開啟（自動載入佇列第一篇，不用先看列表）
2. 掃描成品膠捲 9 張（5 到 10 秒，看的是成品不是候選）
3. 處理待決項 0 到 3 個（只有 block/warn 的張會進待決列）
4. 核准 → 磁吸落 slot → 自動載入下一篇
```

**核心機制：預選 + 例外。** 系統對每張都已做出建議選擇（策展最高分且規則過關），Jesse 只被要求處理系統沒把握的部分。頂部待決列顯示「本篇待決 3 項」，J/K 在**待決項之間**跳，不是在 9 張之間跳。

「全部採用建議」一顆按鈕直達最終預覽。但 **block 級（事實 unsupported、CTA 逐字漂移、封面 hook 缺具體錨點或缺口未關）不可被這顆按鈕略過**，必須逐項處理或整篇退回。這是「產出需要被審視」與「關卡太多會疲乏」之間的解法：關卡不是變少，是只在真的有風險時才打斷。

### 4.3 鍵盤映射（全站一致）

| 鍵 | 動作 |
|---|---|
| J / K | 下一個／上一個待決項 |
| `[` / `]` | 上一篇／下一篇 |
| 1 到 9 | 跳到第 N 張 |
| E | 編輯本張文案 |
| G | 為本張生成替代圖 |
| A | 核准 |
| R | 退回重寫（帶原因輸入） |
| S | 排程（開 slot 選擇器） |
| ? | 快捷鍵表 |

**核准後直接載入下一篇而不回佇列**，這是單點節省最大的一項 **[推理]**。

### 4.4 影子模式（上線前的安全網）

任何新檢查規則上線後先跑兩週「只記錄不阻擋」，統計 Jesse 的推翻率。只有推翻率低於 10% 的檢查，才允許升級成「自動預選並收進 L2」。推翻率高的規則要嘛調閾值，要嘛廢掉。這條防止新規則把審稿時間反向拉長。

## 5. 漸進式揭露

三層，判準是使用頻率而不是重要性。

| 層 | 取得成本 | 內容 |
|---|---|---|
| **L1 常駐** | 0 次點擊 | 階段色條、閘門四點、待決計數、主要動作（核准／退回／排程／放行）、成品預覽、頂欄健康列 |
| **L2 一次點擊或 hover** | 1 次 | 候選圖全池、查證細節與出處、heat_evidence、逐條檢查說明與建議改寫、變更歷史、單篇成效 |
| **L3 另一個面板** | 2 次以上 | 來源開關與費率、prompt 模板、所有閾值、模型與成本、A/B 設定、版本回滾、原始 JSON 檢視 |

判準一句話：**一週用不到一次的控制項，不得出現在主動線。**

三個具體歸位決策：

- **生成（環節 4）不是一個面板**。它是審稿台選圖區裡的一顆「生成替代圖」按鈕（L1），以及規則面板裡的 prompt 模板與配額（L3）。理由：決策樹已定為機器自動判斷，人只在補位時才碰它。
- **提案／討論功能不做**（已定案），雷達面板不放任何評論欄。
- **原始 JSON 檢視必須保留在 L3**。一人團隊沒有工程支援，這是逃生口。

## 7. 技術可行性

結論：**這套設計在 GitHub Pages + vanilla JS + GitHub API 架構下九成可行，但有一個會在約 9 週後撞牆的硬限制必須先處理。**

### 7.1 必須先修：`posts.json` 逼近 GitHub Contents API 的 1MB 讀取上限

- 實測：`data/posts.json` 473KB / 25 篇，約 19KB／篇 **[驗證]**
- `app.js:42 apiGet()` 走 contents API 的 base64 `content` 欄位；GitHub 文件說明 1MB 以上僅支援 raw／object media type **[驗證，二手：GitHub REST 文件]**
- 推算：約 53 篇時**整個操控室讀不到資料，全站掛掉**。以 3 篇／週計約 9 週 **[推理]**

**解法**：拆成 `data/posts/index.json`（每篇只留看板卡片需要的 20 個欄位，估 1KB／篇，可撐 1000 篇）＋ `data/posts/{id}.json`（逐篇重物，含候選清單）。審稿台進入一篇時才載入該篇。這同時解掉 7.2。

**這件事應併入 B0，不是 B1。** 它是資料層改動，越晚做遷移成本越高。

### 7.2 寫入衝突：拆檔後自然收斂

`saveJson()` 已有 SHA 樂觀鎖與 3 次 409 重試 **[驗證，`app.js:57`]**，但目前每次核准都重寫整個 473KB 檔案，而哨兵每 10 分鐘也在 push 同一個檔。拆檔後衝突面縮到單篇，撞車機率趨近於零。日曆拖拉的批次改期仍會碰 index.json，需保留重試並在失敗時回滾 UI 加 toast。

### 7.3 不需要突破：「靜態頁觸發跑批」這條路已經存在

`auto_render.sh` 由 launchd 每 600 秒執行，做 git pull → render-approved → push，且是冪等的 **[驗證]**。所以前端所有「動作」的正確模型是**寫入意圖，由哨兵接手**，不需要 GitHub Actions（repo 目前沒有任何 workflow **[驗證]**）。

需要調整的只有兩件小事：

1. 審稿台按「生成替代圖」要等 10 分鐘不可接受。加一個 60 秒間隔的快車道 watcher，只處理 `data/jobs/urgent/*.json`。改一個 plist 數字加一支 20 行腳本。
2. 哨兵要寫心跳檔 `data/heartbeat.json`（時間、Drive 掛載、本輪處理數），供頂欄健康列讀取。目前 Drive 未掛載是靜默 exit，這是現行最容易讓人乾等的失效模式。

### 7.4 圖片載入：現況已對，但縮圖尺寸要改

`publicRaw: true`，圖片走 raw.githubusercontent.com 不吃 API 額度 **[驗證，`config.js`]**。但 `_thumbs.py` 產的是長邊 1080 **[驗證]**，候選 grid 一次載 20 張等於 20 張 1080 圖。建議加產 256px webp 專供 grid，1080 留給主舞台與燈箱。
raw CDN 的快取延遲會讓剛 push 的成品有短暫看不到的窗口 **[待查，未實測延遲長度]**，UI 需在圖片載入失敗時顯示「成品剛產出，約 1 分鐘後可見」而不是紅色錯誤。

### 7.5 前端結構：不上框架，但必須模組化

869 行單檔 vanilla JS 要再承載看板拖拉、日曆磁吸、鍵盤流、三欄同步，會失控。建議：

- 拆成 ES modules（`store.js` / `router.js` / `panels/*.js` / `components/*.js`），Pages 原生支援 `<script type="module">`，**不需要 build step**，這是現行架構最值得保住的優點。
- 加一個極小的 store（單一 STATE 物件 + 訂閱），取代現在 `render()` 整頁重畫的做法。三欄同步與樂觀更新都需要它。
- **不要上 React／Vue**。引入 build step 會讓「Claude 直接改一個檔就部署」這條開發動線消失，對一人團隊是負收益。

### 7.6 憑證

PAT 存 localStorage 是現況，桌面優先後不變。要做的只有兩件：權限最小化為單 repo `contents:write`，以及唯讀模式的視覺標示要比現在明顯（現行是一條容易被忽略的 banner）。**不做前端加密**，那是假安全。

## 8. 需要 Jesse 拍板的五個決策

1. **著陸頁的例外規則**（積壓 ≥6 時強制導向審稿台）要不要做。這會在你「只想看看日曆」時擋路。
2. **「等你」欄 WIP 上限設 6** 是否合理。現況 14，上限太低會天天紅燈，太高就失去訊號。
3. **品牌橘只用於「需要你」** 這條約定要不要接受。代價是操控室整體看起來會比現在冷。
4. **`posts.json` 拆檔併入 B0**，這會讓 B0 從 2 天變 4 天，但避免 9 週後的全站故障。
5. **B4 成效面板刻意排在第五批**，代表未來約兩個月成效仍然只能看現在的簡單列表。
