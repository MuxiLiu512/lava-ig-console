# 排程環節升級設計（環節 6）

## 0. 一句話結論

問題不是「缺日曆」，是**排程沒有可決策的維度**：現在只有一個 `datetime-local` 輸入框（`docs/app.js:529`），時間憑感覺、組合無人管、發佈靠輪詢。

三個改動綁在一起才有意義：**時段白名單**（把連續時間軸壓成 5 個 slot）→ **週配額規則**（管內容組合）→ **slot 觸發發佈**（取代輪詢）。第三項不只是精度問題，是成本問題，見第 5 節。

## 1. 最佳發文時間

### 1.1 外部證據（兩個台灣數據源，互相衝突）

| 來源 | 樣本 | 結論 | 可信度 |
|---|---|---|---|
| [QSearch 2026-07](https://www.qsearch.cc/blog/2026/07/the-best-time-to-post-on-instagram/) | 450 萬則台灣貼文 | **20:00-21:00 全週最強**；週二總量約週一 2.5 倍；週六 12:00 為全週最強午間；05:00-06:00 最低 | 高（台灣本地、樣本大） |
| [IG HERO](https://www.ig-hero.com/) | 2,500 台灣帳號，2025-01 至 2026-05 | 週一 11-13、週二 8-9／13-14、週三 19-21、週六 9-11 | 中低（成長服務商自產，方法未公開細節） |

**[推理] 我對 QSearch 方法的保留**：它算的是「高互動貼文密度」，不是「同一篇在不同時段發的差異」。20:00 發文供給量本來就最大，高互動貼文自然集中在那裡。這是供給混淆，不是因果。所以外部數據只能用來**縮小候選 slot**，不能拿來當結論。

**[驗證] 演算法面**：Mosseri 確認的主排序信號是 watch time、sends per reach、likes per reach（[Hootsuite](https://blog.hootsuite.com/instagram-algorithm/)、[dataslayer](https://www.dataslayer.ai/blog/instagram-algorithm-2025-complete-guide-for-marketers)），且**排程發佈不會被降權**。時間只決定「初始曝光窗口打在誰身上」，之後由互動接手。對 200 追蹤的帳號，初始窗口幾乎全打在既有粉絲上，所以時段的作用是「粉絲在不在線」，不是「演算法喜不喜歡」。

### 1.2 建議 slot（台灣時間，鎖死不再手動輸入）

| Slot | 時間 | 內容定位 | 依據 |
|---|---|---|---|
| S1 | 週二 20:30 | 主打（知識型/最有把握的一篇） | 週二總量最強 × 晚間峰值 |
| S2 | 週四 20:30 | 次打（時事/趨勢詞） | 晚間峰值，與 S1 間隔 48h |
| S3 | 週六 12:30 | 輕量（人物志/品牌） | 週六午間為全週最強午間 |
| S4 | 週日 21:00 | 收藏型（清單/金句卡） | 週日峰值後移，收藏行為集中 |
| HOT | 平日 12:30 | 熱點 buffer，預設空著 | 午休窗，時效內容不必等到晚上 |

**為什麼是 :30 不是整點** [推理]：整點是品牌發文供給高峰，同時也是 cron 系統壅塞時段（[GitHub 官方](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)：「High load times include the start of every hour」）。錯開 30 分同時避開競爭與技術延遲。

### 1.3 用自己的數據校準（現在還做不到，先講為什麼）

**現況硬事實**（我實際讀了 `data/insights.json`）：

- 只有 5 篇有成效快照，且**快照日齡不同**（D8/D4/D6/D2/D4），reach 不可橫向比較
- 這 5 篇發佈時間換算台灣時間分別是 14:01、13:01、00:33、11:01、12:01，**沒有任何一篇落在 20:00-21:00**。建議的主 slot 從來沒被測過
- 25 篇 `topic_type` **全部是 `A-知識型`**，型式變因無法控制
- 8 月 5 篇 `media_id` 剛補回，尚無快照

結論：**現在做任何時段歸因都是瞎猜**。校準要先修基礎設施。

**校準協議（三步，可執行）**

1. **修 WF11 的取樣規則**：改成每篇固定在 **D1 / D3 / D7 / D28** 各拉一次（現在是隨機日）。`insights.json` 每篇加三個欄位：`slot_id`、`published_hour_tw`、`weekday`。沒有固定日齡就沒有可比數字，這是前提，不是加分項。
2. **主指標用 `reach@D3 中位數` 與 `sends/reach`**，不用平均值（n 小、長尾嚴重）。sends 是 Mosseri 明講的非粉絲擴散信號，比 likes 更接近「會不會破圈」。
3. **實驗設計**：S1 與 S3 做配對輪替（同 `template_id` 的兩篇分別排在兩個 slot）。**誠實的樣本估算**：現在 reach 落在 200-260，要偵測 30% 的 slot 差異，每組約需 12 篇，每週 3 篇 → **約 8 週才有結論**。這期間不要一直換 slot。

**免費且立即可用的內部真相**：IG App 專業儀表板 → 粉絲 → 最活躍時間。帳號需 ≥100 追蹤（Lava 約 200，符合）。Jesse 手動看一次，截圖存進 repo 當基準。

**API 端 `online_followers`**：[待查]。Meta 現行 Instagram Platform insights 文件**只在限制段落提到它**（「Insights data for the `online_followers` metric is only available for the last 30 days」、「not available on accounts with fewer than 100 followers」），**沒有列在支援指標表**。可能是殘留文字，也可能仍可查。實測指令：

```bash
curl -G "https://graph.facebook.com/v23.0/{ig-user-id}/insights" \
  -d "metric=online_followers" -d "period=lifetime" \
  -d "access_token=$IG_TOKEN"
```

回 200 就接進 `ig_insights.py`（該檔目前是骨架，`scripts/ig_insights.py:40` 還是 TODO）；回 error 就以 App 內數據為準，不推估。

## 2. 內容節奏規劃

### 2.1 現況不是「要預防同質」，是**已經 100% 同質**

`posts.json` 25 篇：`topic_type` 全為 `A-知識型`。`templates.json` 有 20 個模板（11 validated、9 candidate，涵蓋趨勢詞策展、數據反差、原型圖鑑、時事挪用、產品機制圖解等），**實際只跑了知識型一種**。庫存裡另有 3 篇同以「欸…你有沒有發現」開場。

### 2.2 週配額（3 篇/週）

一週 3 篇對應兩件事：Mosseri 講的「一致性重於數量」，以及 Jesse 是唯一瓶頸（現在 `awaiting_review` 積壓 14 篇）。

| Slot | 型式配額 | 對應 template 群 |
|---|---|---|
| S1 週二 | 知識型 A | `tpl-data-contrast-hook`、`tpl-life-decision-mustread` |
| S2 週四 | 時事／趨勢詞 B | `tpl-trend-word-textcard`、`tpl-newsjack-oneliner-collage` |
| S3 或 S4 | 品牌／人物志 C | `tpl-product-intro-carousel`、`tpl-archetype-catalog-carousel`、`tpl-offline-recap-carousel` |
| HOT | 空著 | 週四 12:00 前未填，自動由候選池最高分的常青篇遞補 |

### 2.3 六條可機器驗證的節奏規則

新增 `scripts/rhythm_check.py`，讀 `posts.json` + `templates.json`，回傳 `violations[]`：

| 代號 | 規則 | 治什麼 |
|---|---|---|
| R1 | 相鄰兩篇（依 `publish_at`）`topic_type` 不得相同 | 現況 25/25 同型 |
| R2 | 連續三篇不得同 `template_id` | 版型節奏停滯（WF15 已多次指出） |
| R3 | 同一 `hook_type` 7 天內至多 2 篇 | 「欸…你有沒有發現」濫用 |
| R4 | `timeliness=newsjack` 的篇，`publish_at` 須在 `heat_evidence` 抓取後 72h 內，否則自動降級 draft | 熱點過期還在排 |
| R5 | 每週保留 1 個 HOT slot；週四 12:00 未填則自動遞補常青篇 | 突發熱點沒位置 |
| R6 | 30 天內 `topic` 語意相似度 > 0.85 擋下 | 撞題（現有去重只比對字面） |

**前置資料改動**：`posts.json` 每篇加 `timeliness`（`evergreen` / `seasonal` / `newsjack`）與 `template_id`。這兩個欄位現在都沒有，而它們是排程決策的核心輸入，沒有它們日曆只是漂亮的日期格子。

## 3. 日曆視圖設計

**預設是週視圖，不是月視圖。** 決策單位是「這週組合健康嗎」，月視圖看不到 slot 內細節，週視圖 5 列 × 7 欄一屏看完。

### 顯示什麼

每格（一個 slot）顯示：
- 封面縮圖 96px（沿用 `docs/finals/` 的成品，不另外做）
- `topic_type` 色條（左緣 4px，A 藍／B 橘／C 綠）
- `hook_type` 徽章（文字，不是 icon，因為要能一眼比對重複）
- 時效標籤（常青／季節／熱點，熱點顯示剩餘小時數）
- 閘門燈（三顆點：qa / render / token），全綠才是實色卡片，否則半透明加虛線框

頂欄「本週體檢」：三個配額圓點（知識／時事／品牌，填滿或空心）、violations 紅字列、以及「距離下一篇發佈 X 小時」。

### 操作

| 動作 | 行為 |
|---|---|
| 拖拉改期 | 只能落在白名單 slot（磁吸）。按住 Alt 才能落到任意時間，落下時警告「非白名單時段，時段實驗數據會被污染」 |
| Drop 後寫入 | 樂觀更新 UI，背景 `saveJson` 寫 `publish_at`。**必須加 409 重試**（現行 `saveJson` 走 GitHub API 帶 SHA，哨兵同時在 push，衝突是必然的，重讀合併後再寫，最多重試 3 次，失敗則回滾 UI 並 toast） |
| 批次 | 框選多張 → 「整批順延一週」「重新分配到本週空 slot」 |
| 凍結 | 距 `publish_at` < 60 分的卡片鎖定，不可拖拉，要先按「取消排程」。對齊 HANDOFF 既有的發佈凍結窗守則 |
| 月視圖 | 只做唯讀熱度圖（哪週太空／太滿），不支援拖拉 |

## 4. 看板視圖設計

**依狀態分欄，不依日期，不依內容類型。** 日期是日曆的職責，內容類型用色條表達就夠了，切成欄會讓「卡在哪」這件事看不見。

| 欄 | 對應資料 | WIP 上限 |
|---|---|---|
| 1 靈感放行 | ClickUp 已勾選、尚未撰稿 | 8 |
| 2 在製中 | 撰稿／圖搜／渲染中 | 6 |
| 3 **待我審** | `status=awaiting_review` | **6（現在 14，已在紅區）** |
| 4 已核准待排 | `approved` 且 `qa.pass=true` 且成品就緒 | 無 |
| 5 已排程 | `scheduled`，卡片上顯示 slot 名而非時間字串 | 無 |
| 側欄「卡住」 | `render_note` 有值／`qa.pass=false`／有 0 候選 slide | 無 |

**分工一句話**：看板回答「**有沒有東西可以發、卡在哪**」；日曆回答「**發出去的組合對不對**」。

**預設落地頁是看板**，因為瓶頸在審核不在排程。日曆是每週進去一次的規劃動作（建議週一早上）。

第 3 欄的 WIP 上限是北極星（每篇消耗的 Jesse 分鐘數）的前導指標：積壓變多代表單篇成本上升或產能過剩，兩種都要處理。

## 5. 發佈可靠性

### 5.1 該不該改：分兩層答

**對觸及的影響**：[推理] 在 reach 200 級距、主信號是 sends 與 watch time 的前提下，±15 分的延遲對觸及的影響**測不出來**。單看這一點不值得改。

**真正的理由是成本**：[驗證] n8n 官方文件明講「Schedule Trigger: Count one execution every time the node fires」，只有 polling trigger 找不到新資料才不計。15 分輪詢 = 96/日 = **2,880 執行/月**。[驗證] n8n Cloud Starter = **2,500 執行/月**，超額直接停掉所有工作流，沒有寬限、沒有加購。

**光排程輪詢就吃掉 115% 的月額度**，而 HANDOFF 記載的 0723 全線停擺事故根因之一正是額度用罄。這不是最佳化，是拆彈。

### 5.2 三案比較

| 方案 | 延遲 | 執行數/月 | 風險 | 改動 |
|---|---|---|---|---|
| A 維持 15 分輪詢 | ≤ 17 分 | 2,880 | 額度爆掉會全線停擺 | 0 |
| **B slot cron（建議）** | **< 60 秒** | **約 22** | 低 | 半小時 |
| C 事件驅動 Wait-until | 趨近 0 | 約 12 | 中高 | 半天 |

**B 的做法**：WF10 的 Schedule Trigger 改成只在白名單 slot 觸發（`29 20 * * 2,4`、`29 12 * * 6`、`0 21 * * 0`、`29 12 * * 1-5`），`Pick Due Slides` 的條件從 `publish_at <= now` 改成 `publish_at 落在 now ± 10 分鐘`。

B 有一個隱藏紅利：**視窗化條件天然解掉過期重貼**。現在 `archived-posts.json` 有兩篇過期 `scheduled`，只要被任何一次輪詢撿到就會被重貼；改成 ±10 分鐘視窗後，過期太久的永遠不會被撿起來。

**為什麼不建議 C**：改期／取消要能取消掛起中的 execution，n8n 沒有乾淨的 API 做這件事，得在 execution 內自己回頭核對 `posts.json` 才能決定要不要發，補償邏輯比省下的 60 秒貴。另外 [待查]：掛起執行算一次還是兩次執行，只有 [社群共識](https://community.n8n.io/t/do-wait-nodes-create-new-executions-or-resume-the-same-execution/200337)（回答者非官方），官方文件沒寫。而且 [驗證] Wait 節點「always uses n8n server time regardless of the timezone setting」，台灣時間要自己換算，多一個出錯面。

### 5.3 必加的保險

- **每日 23:50 對帳 cron**（30 執行/月）：找出 `status=scheduled` 且 `publish_at < now - 30 分` 的，開 ClickUp 告警卡。**不自動補發**，半夜自動重貼比漏發更糟，補發由人決定。
- **Token 存活檢查**：IG 長效 token 60 天。排程日超過 token 到期日就不准排（見閘門 H7）。
- **配額真值**：`GET /{ig-user-id}/content_publishing_limit`。註記一個查證衝突：[Meta 現行文件](https://developers.facebook.com/docs/instagram-platform/content-publishing)寫「limited to **100** API-published posts within a 24-hour moving period」，多數第三方指南仍寫 25。Lava 一天 1 篇不會撞到，但閘門應該讀真值而不是寫死常數。

**成本**：B 案月增 $0，n8n 執行數從 2,880 降到約 55（22 + 30 對帳）。省下的額度足夠讓環節 1 的多來源選題擴張。

## 6. 排程前的最後閘門

已定案 `qa.pass === true`。但現況顯示光這一條不夠：`20260728-AzizAnsari` 是 `published` 且 `qa.pass=false`，`qa.ts` 比 `publish_at` **晚兩天**。閘門不只要存在，還要**時序正確**。

### 硬擋（不通過按鈕 disabled）

| # | 條件 | 驗證方式 |
|---|---|---|
| H1 | `qa.pass === true` **且** `qa.ts > rendered_at` | 時戳比較 |
| H2 | 張數 ≤ 10，每張 `public_url` HEAD 回 200 且 `Content-Type: image/jpeg` | IG 輪播上限 10 張、JPEG only |
| H3 | 每張比例落在 4:5 到 1.91:1、寬度 320-1440 px | 見下方 [待查] |
| H4 | `rendered_at` > 最後一筆 `copy_edits` 時戳 | 防 stale render |
| H5 | caption ≤ 2,200 字元、hashtag ≤ 30 | IG 上限 |
| H6 | `publish_at` 在白名單 slot 且 ≥ now + 30 分 | 留重出成品的時間 |
| H7 | `publish_at` < IG token 到期日減 3 天 | 60 天長效 token |
| H8 | 該 slot 沒有其他 `scheduled` | 唯一性 |

**H3 的 [待查]**：官方文件寫最大寬度 1440 px，排版引擎畫布是 **1950×2438**。IG 會自動降尺寸，但降完的畫質沒人驗過，而這條管線的賣點就是排版精緻度。建議實測：抓一篇已發佈貼文的 `media_url`，比對實際交付尺寸與本地成品。若確認被降到 1440，排版引擎應改為直接輸出 1440×1800（省頻寬、可控銳利度）。這是我在這份設計裡查到的、影響最直接的一個既有問題。

### 警告（可覆寫，但要勾選確認）

W1 節奏違規 R1-R3｜W2 newsjack 超過 72h｜W3 30 天內語意重複｜W4 `image_credits` 缺漏（授權策略是引用式使用加出處標注，缺標注等於把風險留在自己身上）

### 實作位置

`scripts/schedule_gate.py`（純本機、零 AI 呼叫）+ 操控室按鈕綁定。**同時 WF10 的 `Pick Due Slides` 保留最小複檢**（`qa.pass !== false`、`!no_publish`、非 demo）作第二道。理由：前端閘門可被繞過（任何人可以直接改 repo 的 JSON），而 HANDOFF 已記載過一次資料被無聲回退的事故。
