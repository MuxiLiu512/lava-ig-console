### 0.3 產能 12 篇/月，所以 90 天內任何以 reach 為結果變數的實驗都測不出來

## 1. 核心判斷

### 1.1 決定成敗的是環節 2 與環節 5，其餘五個是支援

**依據是算術，不是偏好。**

現況 reach 200 到 260、追蹤 200，reach/follower ≈ 1.0 到 1.3 **[驗證，`insights.json`]**，代表幾乎全部觸及來自既有粉絲。要到 2,000，必須有八到九成觸及來自非追蹤者，也就是必須進推薦流。推薦流的燃料是 sends per reach 與 watch time。

七個環節裡真正能動 sends/reach 的只有兩個：

| 環節 | 對 sends/reach 的作用 | 判斷 |
|---|---|---|
| **2 撰稿與審文案** | 結構決定「看完會不會轉給特定的人」。現況 25 篇全是 `A-知識型` **[驗證]**，說教型內容天然不利分享 | **決定成敗** |
| **5 圖文合併與版型** | 版型決定「滑不滑得下去」與停留時間。現況 `render_post_v5.py` 只有 `render_cover` 與 `render_content` 兩個函式，九張同一個框 **[驗證]** | **決定成敗** |
| 1 選題 | 每週只挑 3 題，供給早就過剩（今日 170 則訊號）。選題精度不是瓶頸 | 支援 |
| 3 圖搜策展 | 天花板被法遵與圖庫同質性鎖住，補得再好只是「不刺眼」 | 支援 |
| 4 圖片生成 | 五種需求裡只有兩種需要生成，且都不是瓶頸 | 支援，90 天內延後 |
| 6 排程 | 200 追蹤的帳號，時段只決定粉絲在不在線，效果量小且測不出 | 支援 |
| 7 成效 | 不創造觸及，但**它現在是壞的**，是所有東西的前置 | 前置條件 |

### 1.2 具體到一個可執行的主張

**環節 2 × 環節 5 的交集，就是 Jesse 今天提的人物／書籍／概念題。**

它同時打兩件事：內容從「教你怎麼約會」的說教位置，換到「講一個人怎麼活」的敘事位置（分享說教像在教訓朋友，分享人物故事不會，這直接打 sends/reach）；同時它的骨架（時間軸證據鏈、引言證言鏈）**必須**有對應版型才做得出來，逼出版型庫這件事。

所以整個 90 天的主線就一條：**把「人物／概念題 × 版型庫」做出來，其餘六個環節只做「不會斷」的最小改動。**

### 1.3 一個 Jesse 沒問、但我必須放進來的判斷

**七份文件全部圍繞輪播，零篇處理 Reels。** 2026 年 IG 的分發主力是短影音，用低分發權重的載體追 10x 是把工程做在錯的地方。

而且這是**唯一一個效果量大到在 n=36 就測得出來的變數**（載體差異通常 2 到 5 倍，內容微調通常 10% 到 20%）。工程成本是一支 ffmpeg 腳本（成品 PNG 已存在，ffmpeg 已是 forager 的依賴 **[驗證]**）。

我把它排進 B3，當作 90 天內唯一一個 reach 實驗。詳見決策 5。

## 2. 七環節升級方案

### 環節 1｜主題搜尋

**現況問題（一句）**：來源已從 3 擴到 33 個且今天全部 ok，但收斂層還沒實作，所以擴張只放大了歐美名人八卦的供給，台灣在地訊號幾乎沒變。

**今天的實跑證據 [驗證，`data/signals/latest.json` 2026-08-13 12:31]**：33 源、170 則、strong 57／weak 23／raw 82／未標 8。分佈是 global_pop 13 源、tw_local 11 源、mind 7 源。但 tw_local 今日產出：中央社生活 1、中央社社會 0、自由時報 2、ETtoday 5、PTT 三板共 8、女人迷 12（幾乎全業配）、Google Trends TW 10（麥當勞、湖人、道奇）。真正有價值的是兩個 Google News 源共 24 則，命中「交友軟體退流行線下活動正興起」「單身商機吹起主題經濟」「不靠交友軟體出社會怎麼找另一半」「Bumble 允許雙方主動發訊息」「暈船衍生我鹿了」。

**升級後樣子**：採集每日跑但不進 LLM；靈感卡每週兩次（配合批次日生產）；操控室頂欄一顆「來源健康」燈。選題決策動線**留在 ClickUp 不動**。

**關鍵改動（3 項）**

1. **四條 kill rule**（各一行 regex，估砍掉一半雜訊）：標題含 `Complete Relationship Timeline`／`Dating History` 直接丟；女人迷含品牌名或「登台、開箱、直擊、攜手、成果發表」丟；PTT 過濾 `[公告]`／`Fw:`；Google Trends TW 只留人名詞
2. **跨源共振計數**（單一機器指標，取代 S 分六項加權模型）：同一事件出現在 ≥3 個不同源就加冕。這是 S1 全模型最有價值的一項，其餘五項都是猜的
3. **來源健康表接 ClickUp 告警**（約 40 行）：`collect_signals.py` 的 `--health` flag 與 `latest.json` 的 `source_count`／`ok_count`／`sources` 欄位**已經寫好** **[驗證]**，接上 `sync_console.py:1160 alert()` 即可

**任務配置**：採集、kill rules、共振計數、去重、健康表全部純程式 $0。靈感卡組裝用 Sonnet 5（材料已篩過，工作是組裝不是大海撈針），每週 2 次。

**UI 設計**：不做雷達面板。只在操控室頂欄健康列加一顆來源燈（綠／黃／紅），點開是一張 33 列的表格：來源名、今日筆數、最後成功時間。紅燈超過 3 天自動開 ClickUp 卡。這個面板的價值是「哪個源沒在動」，不是給人讀新聞，所以不需要一個獨立頁籤。

**砍掉什麼**：S 分六項加權（Vel/Loc/Fit/Conv/Auth/Rec）、agglomerative clustering、L2 embedding 去重、新鮮度三指標、epsilon 探索抽樣、7 項 rubric、Brier 分離度追蹤。**理由**：這套約 400 行、需要 OpenAI embedding key（repo 目前沒有），服務的是「每週 3 個決策」。而 S1 自己承認校準閉環在 90 天內拿不到統計顯著性，在 12 篇/月下只會更差。40 行的健康表價值高於 400 行的評分模型。

### 環節 2｜撰稿與審文案

**現況問題（一句）**：25 篇全是知識型、44% 撞同一個開場、非 CTA 的 177 張裡 47% 超過 140 字（中位 139、P90 217、最長 321）**[驗證]**，字數在自己漂移而沒有任何機制在擋。

**升級後樣子**：撰稿走 Opus 5 並開配對盲測 A/B；14 條機械檢查先跑影子模式兩週再升 block；模板決定張數與角色，撰稿只填內容。

**關鍵改動（3 項）**

1. **撰稿切 Opus 5，參數要對**：`thinking: adaptive`、`effort: high`、`max_tokens: 32000`（Opus 5 的 `max_tokens` 同時蓋住 thinking 與正文，沿用 Sonnet 時代的值會讓第 9 張被截斷且不報錯）。同時把 WF01 研究步驟的 `web_search_20250305` 換成 `web_search_20260209` **[驗證，HANDOFF:246]**，不然新模型跑舊工具，白付 Opus 的錢拿到比較差的檢索
2. **定向改寫改參數，並加一條檢查**：任務配置原本寫 `thinking: disabled` + `effort: high`，這是錯的。Opus 5 在 thinking 關閉下有兩個記載在案的失效模式（tool call 被寫進可見文字、`<thinking>` XML 洩進輸出），而改寫輸出直接進 `display_copy`、直接被 `render_content` 印在圖上，而 14 條檢查沒有一條擋 XML 標籤。**改成 `thinking: adaptive` + `effort: low`**（成本一樣降，兩個失效模式都消失），並加 `no_xml_tags` 檢查（五行）
3. **14 條機械檢查全部先跑影子模式**：`over_length`（>140 block）上線第一天會擋掉現有 47% 的張。所有新 block 規則一律先「只記錄不阻擋」兩週，Jesse 推翻率 <10% 才升級。**這條升為跨環節硬約束，寫進 config，不是 UIUX 裡的一小節**

**任務配置**

| 任務 | 執行者 | 理由 |
|---|---|---|
| 結構變體選型 | 純程式讀 `templates.json` | 觸發條件全是機器可判 |
| **撰稿** | **Opus 5** adaptive/high/32k | 唯一「品質直接等於成效」的環節 |
| A/B 對照稿 | Sonnet 5，**共用同一組 `visual_refs`** | 兩稿圖不同就無法歸因到文案，這是最容易漏掉的一條 |
| 14 條機械檢查 | 純程式（Python + 前端 JS 各一份） | 前端那份把回饋從 10 分鐘壓到 0 秒 |
| 定向改寫 | Opus 5 adaptive/low，只餵標紅的 slide | 同模型保語感，只改壞的 |

**UI 設計**：審稿台右欄的文案編輯框，違規詞用底線標出，滑過顯示規則代碼與建議改寫，一鍵採納。左欄是判決區（可上／N 項待處理／不可上，大字），**預設全部摺疊，只有被標紅的展開**。編輯後即時重跑機械檢查。**不顯示任何裸分數**（不顯示「Hook 分數 82」），改顯示「通過 4/6 項」加未通過清單，因為那些權重全是拍的，一個看起來像預測力的數字會讓 Jesse 開始據此決策，那比沒有規則更糟。

**砍掉什麼**：S2 的四種結構變體 V1/V2/V3/V4。**理由**：它們與 S3 的九張節奏合約、S5 的 save_card 固定倒數第二張互相矛盾，V3（6 張，收藏卡就是揭露那張）讓「每個變體有且只有一張 save_card」直接不成立。**改成張數與角色由 `templates.json` 的 `slides[]` 定義，模板是唯一真理來源。** 也砍掉事實查證的 L2 判讀層（見環節 2b 的替代做法）。

### 環節 3｜圖片 ref 搜尋與策展

**現況問題（一句）**：問題不是「候選太多要逐張看」，是同篇撞主體與缺料，而且規模比宣稱的小 4 到 6 倍。

**我實測的候選數 [驗證，`posts.json` 25 篇 202 張 slide]**：每張 slide 候選中位數 **4**、最大 12；每篇加總中位數 26、最大 74（74 是整篇加總，只有 3 篇達到）。而 `app.js:252` 已經預選 `default_cid`，`app.js:307` 把該 slide 的候選並排顯示。所以實際動作是捲 9 組各 4 張的縮圖，不是 UIUX §4.1 算的「最多 153 次視覺比較」。

**反而更值得注意的是缺料**：202 張裡 46 張零候選，其中 25 張是 CTA（用公版，正常），另外 **21 張是真的沒有底圖**，集中在「知識解釋」12 張 **[驗證]**。

**升級後樣子**：策展合併成一次呼叫（理由是分數穩定性，不是省錢）；`subject_key` 主體去重；候選圖不合格時走版型解法而不是生成。

**關鍵改動（3 項）**

1. **合併 curate 呼叫，但前置條件要寫清楚**：現況走 n8n webhook（`forage_shots.py:477` `urlopen(req, timeout=150)`），S3 提的「改用 `client.messages.stream()`」是 Anthropic SDK 的 API，**n8n 的 HTTP Request 節點不做 streaming**。要合併就必須先把 WF14 從 n8n 搬回本機直打 API。這條路是通的（`collect_signals.py` 已示範），但必須寫進依賴。金錢報酬每月 $0.20，**真正的理由是相對排序需要看整篇**
2. **`subject_key` 封閉詞表 + Python 執法 R1／R2／R4／R8 硬淘汰**：解掉「四張同一本書封」。`subject_key` 不能讓模型自由命名，用 canonical 前綴表（`person:`／`book:`／`place:`／`object:`／`screen:`／`scene:`）加 Levenshtein ≤2 合併
3. **定序「候選最高分 < 5」的三個互斥處置**：現在 S3 說淘汰、S4 說走生成、S5 說走 brand_solid 版型，誰先跑沒人定義。**定案順序：R3 淘汰不進候選池 → 該 slide 若 0 張合格則走 S5 的 `brand_solid` 版型（零成本、永不卡住、順便解節奏）→ AI 生成排最後，90 天內不啟用**

## 3. 人物／書籍／概念類主題的落地方案

### 3.1 先拆 heavenraven 那篇，並承認三分之二是查證不是創作

Tom Holland 顯化篇的結構：

```
封面斷言（創作）→ 證據鏈 3-5 張（查證）→ 轉折（創作，最難）
→ 第三方證言鏈 3-4 張（查證）→ 收尾原則（創作）
```

**它的說服力不來自文筆，來自「2013 年說想演蜘蛛人、三年後成真」這種可核對的時間線事實，以及 Zendaya、諾蘭、Hemsworth 的具名證言。** 這些全是可機器對帳的東西。而如果證據鏈是編的，整篇就毀了，而且是最容易被抓包的一種毀法：一條編造的名人證言掛在 Lava 官方 IG 上，是品牌傷害不是資料品質問題。

**成功要素按貢獻排序（我的判讀，非量測）**：主角自帶流量（Tom Holland 是全球級 IP，這一條無法移植）＞ 證據密度（可移植）＞ 兩次反轉（可移植，且 `tpl-manifest-proof-chain` 的 `why_it_works` 抓得很準）＞ 第三方證言鏈（可移植，素材最難拿）＞ 圖是主角字是配角 ＞ caption 逐行斷句（成本最低，今天就能改）。

### 3.3 證據鏈的查證機制（批評一指出 P4 不成立，這是修正版）

原方案「HEAD 200 + 頁面含關鍵字 = 完全確定 = $0」**不會運作**。名人時間線的一手來源絕大多數是 YouTube 訪談、有 paywall 的雜誌、或 JS 渲染的頁面。HEAD 200 只證明 URL 活著，不證明那句話在裡面。實際會大量落在 `not_found`，而唯一的出路是 Jesse 人工判讀，那是把成本從錢挪到分鐘數，直接打北極星。

**修正做法：把對帳從「驗證言論」降級成「限制來源型別」。**

| 步驟 | 做法 | 執行者 |
|---|---|---|
| P2 證據蒐集 | `web_search` **限來源白名單**：Wikipedia、Wikiquote、帶結構化引文的 Wikidata、以及有 DOI 的學術來源 | Sonnet 5 + `web_search_20260209`，`max_uses: 8` |
| P3 結構化 | 抽成 `{year, claim, source_url, quote, speaker}[]` | Haiku 4.5，strict structured outputs |
| P4 閘門 | **抽不到結構化出處的 claim 一律不進稿**，不是進人工佇列 | 純程式 |
| P5 轉折 | 「但全歸功於 X 太簡單了」那一句 | Opus 5，併入撰稿 |

產量會掉，但這條線本來就只有 4 篇/月。**寧可少一條證據，不要一條編的。**

### 3.4 結構模板：先把模板從描述變成規格

**現在的卡點是機器跑不了。** `templates.json` 的三個 mind 模板（`tpl-manifest-proof-chain`、`tpl-persona-column`、`tpl-concept-decode`）status 全是 `candidate`，而且**只有 `skeleton` 的散文敘述，沒有 `slides` 結構欄位** **[驗證]**。模板現在是給人看的參考，不是給機器跑的規格。

**第一件事：每個模板加 `slides[]` 陣列，逐張標 role、字數上限、圖片 role、版型。**

| 1 | 斷言封面 | 24 | person | `full_bleed_bottom` + 欄目標籤 |

### 3.5 欄目制：最便宜也最該先做的一件

`tpl-persona-column` 的核心是封面左下角固定欄目標籤。建 2 到 3 個欄目（「Lava 觀察」談現象／「Lava 人物」談人／「Lava 研究」談研究），**實作只需在 `render_cover` 加一段標籤繪製，不到 30 行**。

它同時解掉帳號辨識度（讀者滑到第三次就認得出這是誰家的內容）與 S3 反覆抱怨的節奏問題。這是整個人物線裡投報比最高的一項。

### 3.6 視覺策略：Jesse 想複製的效果，跟 Jesse 自己定的法遵線直接衝突

heavenraven 的視覺是該人物的真實劇照與訪談截圖。S3 §1.6 **[驗證]** 明確寫：TMDB 商業使用需授權（年營收 <$1M 為 $149/月）、Getty Embed 不可裁切排版引擎用不了，且建議「禁止把劇照當滿版情緒底圖，這是最容易被 DMCA 的用法」。

**我不能兩邊都答應。三個選項，這件事我不替 Jesse 決定（見決策 1）：**

| 選項 | 做法 | 風險 | 還原度 |
|---|---|---|---|
| **A（建議）** | 主力用 **YouTube 訪談影格**（`forage_shots.py` 已支援，實測 `yt_frame` 39 張）+ **Wikimedia CC/PD 活動照**（有 `extmetadata` 逐張授權）+ **引述文字卡**（`quote_card` 渲染，零素材依賴）。劇照只在 evidence role 當作品資訊卡並標 TMDB | 低。訪談截圖本身就是 heavenraven 用的元素之一，引用性使用主張強 | **約 75%**，缺的是滿版劇照的電影感 |

## 4. UI/UX 總體架構

### 4.1 導覽結構：90 天只做兩個面板加一條健康列

原 UIUX 提了六個面板（工作台／審稿台／日曆／成效／雷達／規則）。我砍到兩個，理由是每個面板都有維護成本，而且五個面板裡有四個是「每週用一次」的東西。

```
┌──────────────────────────────────────────────────────────────┐
│ 頂欄 40px 健康列                                              │
│ 哨兵心跳 · Drive 掛載 · insights 最後更新 · 來源健康 33/33    │
├────┬─────────────────────────────────────────────────────────┤
│ 左 │                                                          │
│ 導 │                    面板工作區                             │
│ 56 │                                                          │
└────┴─────────────────────────────────────────────────────────┘
```

| 順序 | 面板 | 它回答的唯一問題 | 何時做 |
|---|---|---|---|
| 1 | **審稿台**（預設著陸頁） | 這一篇能不能出 | B2 |
| 2 | **工作台**（看板，輕量） | 有東西可發嗎，卡在哪 | B2 |
| 3 | 成效 | 上一批學到什麼 | B3 |
| ⚙ | 設定抽屜（原始 JSON 檢視、憑證、閾值） | 逃生口 | 沿用現況 |

**著陸頁就是審稿台**，不做工作台優先。原 UIUX 的理由是「工作台承載總覽」，但現況瓶頸確定在審稿（14 篇積壓 **[驗證]**），而沒有任何量測顯示選題或排程是瓶頸。瓶頸在哪就把人放到哪。

**頂欄健康列是最便宜、防「安靜退化」的東西，優先於任何面板。** 它解掉三個已知的靜默失效：`auto_render.sh:25` 在 Drive 未掛載時是靜默 `exit 0` **[驗證]**（Jesse 會看到卡片永遠停在「出成品中」而系統從未說為什麼）、insights 停擺 17 天沒人發現、33 個來源壞掉不告訴人。

### 4.2 跨面板一致性：三個正交維度

現行混亂的根源是把「階段」「品質」「例外」擠在同一組 status 字串裡（`app.js:173` 出現 `approved + publish_at + !blocked = 重出中·排程保留` 這種四層三元運算 **[驗證]**）。

- **維度 A 階段**（單選）：候選／製作中／**等你**／待排／已排／已發
- **維度 B 閘門**（四顆點，固定順序）：`文案 · 事實 · 視覺 · 排版`，位置固定在卡片第二行同一像素，所以「第三顆紅」可以被肌肉記憶
- **維度 C 警示**（最多一個）：卡住／缺料／過期／衝突

**品牌橘 `#E84224` 只用在「等你」一種情境，全站不再有第二個用途。看到橘色 = 我是瓶頸。**

**一條反過度自信的規則**：任何 AI 產生的分數一律不以裸數字呈現。改為「通過 4/6 項」加未通過清單，或「型式相近前例的觸及中位數」。查證結果標「已驗到出處層」而不是綠勾，否則綠燈會被讀成「內容正確」，那比沒有查證更危險。

### 4.3 關鍵路徑：從「逐張決定」改成「例外決定」

```
1. 開啟（自動載入佇列第一篇，不用先看列表）
2. 掃描成品膠捲 9 張（看的是成品渲染圖，不是候選底圖）
3. 處理待決項 0 到 3 個（只有 block／warn 的張進待決列）
4. 核准 → 選 slot → 自動載入下一篇
```

三個機制決定它成不成立：

1. **主舞台是成品不是底圖**。現行流程讓人先選底圖再看成品，順序反了
2. **預選 + 例外**。系統對每張都已做出建議選擇，Jesse 只被要求處理系統沒把握的部分。`J`／`K` 在**待決項之間**跳，不是在 9 張之間跳
3. **核准後直接載入下一篇而不回佇列**。這是單點節省最大的一項

「全部採用建議」一顆按鈕直達最終預覽，但 **block 級不可被它略過**。這是「產出需要被審視」與「關卡太多會疲乏」之間的解法：關卡不是變少，是只在真的有風險時才打斷。

**鍵盤映射**：`J`/`K` 待決項／`[`/`]` 上下篇／`1-9` 跳張／`E` 編輯／`A` 核准／`R` 退回／`S` 排程／`?` 快捷鍵表。

### 4.4 技術可行性的兩個修正

**`posts.json` 拆檔不做，改 10 行修法。** 現況 473KB / 25 篇 **[驗證]**，約 53 篇撞 GitHub Contents API 的 1MB 上限，以 3 篇/週算約 21 週（不是 UIUX 說的 9 週，那是用每日 1 篇算的）。而 `rawUrl()` 已經存在（`app.js:39`），`publicRaw: true` 已經設好 **[驗證]**。**sha 繼續走 contents API，內容改走 raw**，10 行解決，B0 之外不需要 +2 天的拆檔工程。

**前端拆成 ES modules，不上框架。** 869 行單檔要再承載版型預覽、待決列、鍵盤流會失控。Pages 原生支援 `<script type="module">`，不需要 build step。**引入 build step 會讓「Claude 直接改一個檔就部署」這條開發動線消失，對一人團隊是負收益。**

### 4.5 影子模式升為跨環節硬約束

S2 的 `over_length` 會擋掉現有 47% 的張，S5 的 R1-R8 有三條 block，S6 的 H1-H8 全部硬擋。**這些規則沒有一條在現有 25 篇上跑過回歸，而現有 14 篇 awaiting_review 是用舊標準寫的，新規則一上會全變 block。**

**寫進 `config/rules-policy.md`：所有新 block 規則先跑兩週影子模式（只記錄不阻擋），Jesse 推翻率 <10% 才升級成 block。** 這條原本只寫在 UIUX §4.4 的一小節，而 S2／S3／S6 的施工表都是直接上 block，這個矛盾沒有人整合。

### 6.3 三個必須講清楚的成本真相

**一、升級後 AI 成本幾乎不變，所以省 API 錢的最佳化全部不值得做。**

從 Sonnet 4.6 升到 Opus 5，每篇多約 $0.13，12 篇/月 = 每月多 $1.6。這在 $68 到 $198 的總成本裡是雜訊。

**二、prompt caching 在這個節奏下幾乎沒有效果。** Cache TTL 是 5 分鐘（預設）或 1 小時（2 倍寫入成本）**[驗證]**。每 2 到 3 天發一篇，兩次撰稿之間 cache 必然過期。唯一穩定命中的是「撰稿 → 自審改寫」（5 分鐘內）。另外 Haiku 4.5 的最小可快取前綴是 **4,096 tokens**（Opus 5 是 512、Sonnet 5 是 1,024），S3 §5.2 寫的「rubric 800 快取」低於門檻，**會靜默不快取且不報錯**，省錢是零。

但「批次日生產」（例如週日一次產 3 篇）有獨立於成本的價值：Jesse 一次進入審稿狀態處理 3 篇，比分 3 天各進入一次省的分鐘數遠大於快取省的錢。**這條該做，但理由是北極星，不是成本。**

**三、唯一有意義的省錢動作是砍訂閱。**

`collect_signals.py` 已經證明「從 n8n 搬回本機直打 API」可行且更穩（S1 記載理由：n8n 的 workflow 每改一次都要重新發布且連線不穩）。**把 WF01 撰稿、WF13 排隊、WF14 策展、WF15 總檢搬回哨兵，n8n 只留 WF10 發佈與 WF11 insights（執行數 <100/月），可以降回最低階方案。** 量級是每月數十美元，遠大於七份文件裡所有 API 最佳化的總和。

保留 n8n 做發佈的理由是可靠性：本機 Mac 在 slot 時間不一定醒著，雲端 cron 比較穩。這是拿錢換可靠性，值得，但不需要為此付 Pro 的錢。

## 9. 需要 Jesse 決策的五個問題

### 決策 1｜人物題的視覺法遵

**問題**：你想複製的 heavenraven 視覺（真實劇照與訪談截圖），跟你自己定的法遵線（S3 §1.6 禁止劇照當滿版底圖）直接衝突。

**建議：選 A。** YouTube 訪談影格 + Wikimedia CC/PD 活動照 + `quote_card` 引述卡，還原度約 75%，風險低。缺的是滿版劇照的電影感，但 `quote_card` 讓「證言」完全不需要照片，這在法遵上乾淨、在視覺上是設計感、成本 $0。**接受視覺會比對標弱一截。**

### 決策 2｜Lava 要不要談流行文化人物

**問題**：人物題的天花板由人選決定。用 Gottman 或 Arthur Aron，自帶流量差 Tom Holland 三個數量級。

**建議：要，但設兩道門。** 人選必須是台灣 25-34 歲認得的人，且必須有「可查證的時間線事實」（不是只有形象）。每篇收尾必須扣回「見面優先」，且落在「你可以做的一件小事」而非人生道理（Lava 禁說教）。**這是策略決定不是工程決定，我不替你拍。**

### 決策 3｜n8n 降級

**問題**：60€/月 是全案最大現金支出，佔總成本的九成以上，而 API 只佔 2% 到 5%。

**建議：做。** 把 WF01 撰稿、WF13 排隊、WF14 策展、WF15 總檢搬回本機哨兵（`collect_signals.py` 已示範可行且更穩），n8n 只留 WF10 發佈與 WF11 insights，執行數會降到 <100/月，可降回最低階。**這一項的節省大於七份文件裡所有 API 最佳化的總和。** 但這是 2 到 3 天的搬遷工程，需要排進 B1 或 B2，且搬遷期間有停擺風險，所以我不擅自排進路線圖。

### 決策 4｜90 天只跑一個實驗，跑哪一個

**問題**：36 篇排不下 90 篇的實驗預算。

**建議：跑撰稿模型的配對盲測，不跑時段。** 理由是結果變數：以 reach 為結果變數的實驗（時段、封面、hook）在 n=36 全部測不出來；以「Jesse 的選擇」為結果變數的配對盲測 n=20 就有結論（需 15/20 才 p<0.05），而且次要指標 `review_seconds` 是連續型、功效更好，直接對應北極星。**時段不當實驗，直接固定成一組 slot 當常數，消除混淆。**

### 決策 5｜Reels 探針要不要做

**問題**：七份文件零篇處理 Reels，而 2026 年 IG 的分發主力是短影音。這可能是唯一真的能帶來 10x 的槓桿。

**建議：做，B3 排 4 篇/月。** 兩個理由：一是效果量大（載體差異通常 2 到 5 倍，遠大於任何內容微調），所以**它是唯一一個在 n=36 下仍測得出來的 reach 實驗**；二是工程成本極低（成品 PNG 已存在，ffmpeg 已是依賴，做一支把 9 張圖轉 8 秒影片的腳本）。

**但發佈端我沒有驗證。** IG Content Publishing 的 Reels 路徑（`media_type=REELS` + `video_url`）在 Lava 現有 token 與權限下是否可用，我標 **[待查]**。動工前應該先用現有 token 打一次 API 確認，這比寫腳本重要。

## 10. 這份設計最弱的三環

### 最弱：「人物概念題會提高 sends/reach」沒有 Lava 自己的任何證據

整個 90 天主線押在這一條上，而它的全部依據是 Jesse 口述的一篇 27.7k 讚的貼文。**我沒有看過那篇貼文本身，也沒看過該帳號的貼文表現分佈。** 27.7k 裡有多少是 Tom Holland 的功勞、多少是結構的功勞，無法分離。

**正確做法，動工前應該做**：用 IG `business_discovery` 抓 @heavenravenofficial 近 25 篇的 likes 分佈（前提是專業帳號）。**如果每篇都 20k+，27.7k 是常態，結構不是原因，帳號規模才是；如果中位數 2k，27.7k 才是真 outlier，結構才值得移植。** 這一次 curl 應該在 B2 開工前跑，不要先建三個模板。

我沒有跑，因為那需要 IG token 與網路呼叫，超出這份設計文件的範圍。但它是整條主線最便宜的證偽方式。

### 次弱：Reels 探針是我提出的最大槓桿，但我只驗了一半

渲染端確定可行（成品 PNG 存在、ffmpeg 已是依賴）。**發佈端完全沒驗**：IG Reels 的 API 路徑、Lava 現有 token 的權限範圍、以及「9 張靜態圖轉成的影片」會不會被 IG 判為低品質內容而降權，這三件事我全部標 [待查]。

如果第三點成立（靜態圖拼接被降權），這條建議會從「最大槓桿」變成「浪費 4 篇的配額」。**緩解是先做 1 篇單點測試再決定要不要做滿 4 篇/月**，而不是照排。

### 第三弱：九個版型都是紙上設計，沒有一個在 1950×2438 上實際渲染過

`brand_solid`、`save_card`、`top_band` 我有信心（都是既有 primitive 的重組）。**`timeline`（節點高度動態累加）與 `quote_card`（PIL 畫開引號、置中排版走 `wrap_semantic`）是最可能第一次做不出來的兩個**，而它們剛好是人物題的核心版型。若這兩個做不出來，人物題會退化回現行的 `full_bleed_bottom`，整條主線的視覺差異化就消失了。

還有一個連帶風險：**新版型上線會讓 `check_typography.py` 的覆蓋率歸零**，除非「沒有 `text_slots` 就不得進 registry」這條硬約束真的被執行。B0 剛修好的字級對齊，會在 B1 被新版型繞過。這是我在整份設計裡看到最容易踩到的一個回頭坑。
