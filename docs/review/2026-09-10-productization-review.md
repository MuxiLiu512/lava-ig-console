## 1. 這個系統在做什麼

一條自動化的 Instagram 內容產線，服務台灣的線下優先約會 App「Lava」。

```
選題 → 撰稿 → 找圖 → 排版 → 四道閘門 → 人審 → 排程 → 發佈 → 收成效 → 學習
```

- **人只做一件事**：在審稿台逐張確認或退回。其餘全自動。
- **架構原則**：事件溯源。瀏覽器寫事件檔，哨兵（launchd，約 10 分鐘一輪）
  是唯一的狀態寫者，`scripts/state_machine.py` 是唯一的合法變遷表。
- **規模**：27 篇貼文（11 已發佈）、23 個範本、59 條外部知識主張、
  33 支腳本、59 項自我測試、17 條不變量、16 條可開關的自動化慣例。

### 為什麼是事件溯源

早期讓瀏覽器直接改 `posts.json`，出現過「排時間無限迴圈」：
使用者按下排程，事件要等哨兵折疊才生效，期間頁面一重整就看到稿又回到佇列，
於是再排一次。改成事件檔＋單一寫者之後結構性消失。

## 2. 這一輪做了什麼（四項，依序）

起點是 Jesse 的判斷：「系統沒有 up to date 地去讀外面的曝光知識」。
盤點後他是對的，但**原因跟直覺相反**——學習機制很完整，只是全部向內看。

### 2.1 外部知識流入（`scripts/playbook_watch.py`）

四步：抓網頁 → 只留帶數字的主張 → 跟我們的實際設定比對 → 落差開成提案。

**設計上最重要的一點是第四步。** 知識流入如果只產出閱讀清單就等於沒有流入；
它必須落成一個「要不要改」的決定才會影響產出。

**刻意不自動改設定。** 別人的帳號、受眾、市場都跟我們不同，
「某研究說 7-15 秒最好」不等於「Lava 的 Reels 就該做 7-15 秒」。

首跑：12 個來源、59 條主張、3 件提案。

> **請審查**：`gaps()` 只做四條硬比對而不做通用語意比對。
> 我的理由是通用比對會產生大量「看起來相關但無法行動」的提案。
> 這個取捨對嗎？還是我只是懶得處理難的部分？

### 2.2 Reels 觀看時長（`scripts/ig_insights.py`）

外部研究一致把觀看時長列為 Reels 第一訊號。我們原本只抓
reach／saved／shares／likes——那組數字判斷得了輪播，判斷不了影片：
一支 30 秒的 Reels 拿到 400 reach，你不知道是「大家看完了」還是
「大家兩秒就滑走」，而那是完全相反的結論。

兩個設計決定：
- **Reels 指標分成第二次 API 請求**，不跟基礎指標併成一包。理由：
  只要 IG 對其中一個欄位不認帳，整包 400，連 reach 都拿不到。
  多一次呼叫換「新指標壞掉不會弄丟舊指標」。
- **輪播的觀看欄位填 `None` 不是 `0`**。`0` 的意思是「看了 0 秒」，
  `None` 的意思是「這個格式沒有這個指標」。混在一起會得出
  「輪播的觀看時長是 0，所以輪播比 Reels 差」這種假結論。

### 2.3 A/B 三個領域（`scripts/hypotheses.py` 加 `domain` 分派）

Jesse 要三種測試：自家貼文發布、海巡來源、回覆策略。

**不另開三支腳本。** 三者的統計完全一樣（Welch＋效果量，兩個都過才算顯著，
樣本不足會拒絕下結論），差別只在「一筆樣本是什麼、組別怎麼決定、
成效從哪讀」。開三支會變成三份會各自漂移的統計實作。

- **海巡來源**：先修資料缺口。87 筆靈感沒有一筆能對回來源——
  來源資料其實一直都在（`scout`、`evidence[].source`），
  但只被塞進 `desc` 字串裡。抽成結構化欄位並回填。
  **誠實話**：回填後 scout 全部是「Claude」一個引擎、sources 只有 4 筆有值，
  歷史資料不足以比較來源，只能從現在開始累積。
- **自家貼文**：`experiment.py` 寫好之後從來沒被呼叫過。接成每天出計畫，
  **刻意不加 `--commit`**：排程等於決定發佈，那一步要人按。
  它現在每天會說「沒有可排程的稿」——那是真的：5 篇已核准全部卡在閘門。
- **回覆**：系統沒有回覆機制。不做假資料、也不回傳空 dict 假裝「還在累積」，
  直接回一個明確的「還沒有這個能力」並寫出阻塞點：
  誰回覆、回什麼、用哪個帳號權限。那是產品決定不是工程決定。

### 2.4 範本拆解與靈感發想（`template_decompose.py`、`inspire.py`）

**拆解**把參考圖拆成可以照著做的數字。分兩層：
量得出來的（色票、重點色、明暗三段、文字密集區、留白、對比）由程式做；
量不出來的（字型、圖素風格、呈現風格、內文撰寫方式）只整理成題目交出去。

**刻意不假裝字型能自動辨識。** 猜錯會變成「系統說這是 Noto Serif，
於是所有稿都用錯字型」——一個猜出來的答案比一個空白欄位危險，
因為空白會有人去填，猜測不會。

**靈感器**把外部知識、成效、範本三份交叉，找出空白格。不呼叫生成模型：
憑空生成的點子沒有理由可以審查，而沒有理由的建議只能憑感覺接受或拒絕。

## 3. 這一輪最重要的三個發現（都是資料，不是意見）

| 發現 | 數字 | 為什麼重要 |
|---|---|---|
| 貼文沒標範本 | **25 / 27** | 「哪個範本有效」在資料層就無解。不是分析不好，是輸入不存在 |
| 範本從沒用過 | **10 / 11 已驗證範本** | 撰稿實際上只用同一個範本，範本庫是裝飾 |
| 學習迴路是黑箱 | **4 支** | 在跑但沒登記在慣例頁，使用者看不到也關不掉 |

第一項是這一輪最有價值的產出。它不是「我們缺點子」，
是**我們就算有點子也驗證不了**。修這個比加功能優先。

## 4. 我在這一輪修掉的自己的錯（請檢查我修得對不對）

誠實列出，因為這些是我判斷力的樣本：

1. **燒字幕偵測器**（已刪除）
   量「畫面下方橫帶比中段忙」，分不出「有字」與「背景本來就複雜」。
   實測有字幕的畫面被判成乾淨。**寧可不放，也不要放一個查不出錯的偵測器。**
   改成片源分級清單（`config/video-sources.md`），使用者可編輯。
2. **重點色只用 HLS saturation 篩**
   L=0.05 的深褐算出 S=0.5，於是四個「重點色」全是黑。加上亮度區間才對。
3. **`getcolors()` 的回傳順序寫反**（算出來剛好對，但讀的人會被誤導）
   ＋一行 `x if False else x` 的死碼。
4. **字幕語言寫死 zh-TW 優先**
   拿英文的 want 去比中文字幕，命中零。改成全部軌都下載、
   用「哪一軌跟要找的內容比較對得上」來決定。
5. **`rememberDecision` 多呼叫一次而且參數寫反**
   `postEvent` 成功後自己就會呼叫。我照著相鄰程式碼抄，多抄了一步不存在的動作。
   **只跑了語法檢查、點開了面板看長相，但沒有按下確定按鈕。**

第 5 點的教訓最貴：**面板打得開不等於動作跑得動。**

## 6. 怎麼驗證這份文件說的是真的

全部可在 repo 根目錄執行，不需要金鑰：

```bash
python3 scripts/selftest.py            # 59 項，應全過
python3 scripts/verify_invariants.py   # I1-I17
python3 scripts/inspire.py             # 靈感清單，含 §3 的三個發現
python3 scripts/hypotheses.py --dry    # 7 條假說，每條都會說明為何還不能下結論
python3 scripts/playbook_watch.py --dry --limit 4   # 外部知識抓取（需要網路）
python3 -m pyflakes scripts/*.py
```

`scripts/template_decompose.py --dir docs/finals/<任一資料夾>` 可看視覺拆解。

## 7. 產品化還缺什麼（給 teammates 用之前）

1. **多人使用**：目前假設單一使用者。事件檔沒有作者欄位，
   兩個人同時審同一篇會互相覆蓋。
2. **權限**：GitHub PAT 存在瀏覽器 localStorage，等於誰開得了頁面誰就能寫。
3. **上手路徑**：新人要看懂需要讀 HANDOFF.md 加 20 份設計文件。沒有 15 分鐘的入門。
4. **失敗的能見度**：卡彈偵測會推 LINE，但只推給一個人。

我認為順序是 2 → 1 → 3 → 4。**請告訴我這個順序哪裡錯。**
